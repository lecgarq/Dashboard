<objective>
Wire the backend-only sync orchestration: Railway release command runs migrations + Quick Sync shell with hard 5-minute timeout; a separate cron script (configured in the Railway dashboard) runs Deep Sync job submission nightly at 09:00 UTC with overlap guard and alert-on-failure. Both scripts write canonical status to `SyncMeta` and `AccDataConnectorJob`.

This plan implements the **shell** only. Real per-project extraction is Phase 2 (Quick Sync) and Phase 3 (Deep Sync ZIP download + CSV ingest). Phase 1 proves the orchestration works end-to-end with placeholder extraction bodies.

**Scope amendment (per CONTEXT.md):** SYNC-01/02/03/04 in REQUIREMENTS.md are worded as user-triggered UI flows ("User can trigger Quick Sync from the existing ACC sync surface…"). This phase implements them as **server-side only** — there are no in-app trigger buttons. Quick Sync = Railway release step. Deep Sync = Railway cron at 09:00 UTC. Deviation documented in CONTEXT.md "Major scope amendment" block and surfaced again in this plan's SUMMARY.

Purpose: Always-fresh data on deploy + nightly activity export, with email-only failure alerting and zero new infrastructure dependencies (no Redis, no BullMQ).
Output: Two CJS entry-point scripts, an email helper export, a `railway.toml` update, and a cron setup doc for Luis.
</objective>

**Part A — Create `scripts/release.cjs` (pure CJS, no TS imports — RESEARCH Pitfall 1):**

The script does, in order:
  1. Run `prisma migrate deploy` via `spawnSync("npx", ["prisma","migrate","deploy"], { stdio: "inherit", timeout: 60_000 })`. Non-zero exit → log "[release] Migration failed" and `process.exit(1)`. **No alert email on migration failure** (deploy fails fast; Railway shows the error in logs; sending email would block exit and we want fast failure).
  2. Set a `const TIMEOUT_MS = 5 * 60 * 1000` watchdog via `setTimeout` that calls `process.exit(1)` after the cap (CONTEXT-locked hard timeout).
  3. Run `quickSyncShell()` — Phase 1 BODY IS A NO-OP: it instantiates Prisma via `require("@prisma/client")` + `require("@prisma/adapter-pg")`, then calls `prisma.syncMeta.upsert({ where: { id: "quick" }, create: { id: "quick", lastRunAt: new Date(), lastStatus: "success", lastError: null }, update: { lastRunAt: new Date(), lastStatus: "success", lastError: null } })`, then `prisma.$disconnect()`. Log `[release] Quick Sync shell complete (Phase 2 will fill in real extraction).`
  4. On any thrown error in steps 2-3, in `catch (err)`:
     - Best-effort upsert `SyncMeta('quick')` with `lastStatus: "failed", lastError: err.message`. Wrap in try/catch (if Prisma is the thing that failed, we cannot write back).
     - Best-effort send failure email via **inline raw fetch to Resend** (cannot import `lib/server/email.ts` from CJS — see Task 1 Note). Use `RESEND_API_KEY` env var. POST `https://api.resend.com/emails` with body `{ from: process.env.RESEND_FROM || "alerts@…", to: "luis.ecorteg@gmail.com", subject, html }`. Wrap in try/catch so email-send failure does not mask the underlying error. If `RESEND_API_KEY` is absent, log a warning and continue.
     - `clearTimeout(timer); process.exit(1)`.

**Use `spawnSync` not `exec` (RESEARCH anti-pattern).** Use relative paths only — no `@/` aliases.

**Part A — Create `scripts/deep-sync.cjs` (pure CJS):**

Order of operations:
  1. Instantiate Prisma client inline (same pattern as Task 2's release script).
  2. **SYNC-04 overlap guard:** `const inFlight = await prisma.accDataConnectorJob.findFirst({ where: { status: { in: ["pending","running"] } }, orderBy: { startedAt: "desc" } });` If `inFlight` exists, log `[deep-sync] Skipping — previous job ${inFlight.requestId} still ${inFlight.status}`, upsert `SyncMeta('deep')` with `lastStatus: "skipped"`, `lastError: "previous still in-flight"`, then `process.exit(0)` (non-fatal — cron continues nightly).
  3. **Fetch 2-legged Autodesk token** via raw fetch to `https://developer.api.autodesk.com/authentication/v2/token` using `APS_CLIENT_ID` + `APS_CLIENT_SECRET` env vars, scope `account:read data:read data:create` (matches Task 1 Part B). Standard OAuth client_credentials grant POST.
  4. **Resolve accountId:** Read `prisma.project.findFirst({ select: { apsHubId: true } })`, strip `^b\.` (inline strip — cannot require the TS helper from Plan 02 in a CJS script; this is one of the call sites and is documented as a deliberate dual-implementation. The Plan 02 helper still owns the canonical version for TS callers; the CJS script duplicates ~3 lines for self-containment).
  5. **Submit Data Connector job:** POST `https://developer.api.autodesk.com/data-connector/v1/accounts/${accountId}/requests` with body from `01-RESEARCH.md` "APS Data Connector — job submission" section. Use `serviceGroups: ["activities","admin"]`, `dateRange: "PAST_7_DAYS"`, `scheduleInterval: "ONE_TIME"`. Capture `{ id: requestId }` from response.
  6. **Persist `AccDataConnectorJob`:** `prisma.accDataConnectorJob.create({ data: { requestId, status: "pending", serviceGroups: ["activities","admin"], dateRange: "PAST_7_DAYS", startedAt: new Date() } })`.
  7. Upsert `SyncMeta('deep')` with `lastStatus: "success"` (sync **submission** succeeded — the actual job lifecycle is tracked separately in `AccDataConnectorJob`).
  8. **On any thrown error in steps 3-6:** mirror the release-script failure path — best-effort `SyncMeta('deep')` upsert with `lastStatus: "failed"` + error message; best-effort raw-fetch Resend alert email with `syncType: "deep"`, `timestamp`, `errorMessage`, and `jobId` if a `requestId` was already captured before the throw; `process.exit(1)`.

Use `spawnSync` or `node-fetch`? **Use the native global `fetch`** (Node 22 has it built-in — confirmed by Dockerfile `FROM node:22`). No new deps.
