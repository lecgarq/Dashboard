# Access-Analysis Slider Sidebar — Polish, Un-package & Folder Reach

**Date:** 2026-05-29
**Branch:** `feat/access-analysis-redesign`
**Status:** Design approved (verbal), pending written-spec review

## Background & problem

The ACC access-analysis graph has a catalog-driven dimension sidebar (~204 dims: 9 structural + ~176 per-action + 19 folder). Investigation on 2026-05-29 established three facts the user asked about:

1. **Folder attributes show "no data" by hardcode, not by missing data.** `dimensionCatalog.folder.ts:18-30` builds all 19 folder dims with `available: false`, `surfaces: []`, `extract: () => null`, with the comment "These live per-folder, not per-(user,project), so there is no node value." The live DB is heavily populated:
   - `AccFolder`: **397,009** rows across **973** projects
   - `AccFolderPermission`: **4,985,821** rows
   - `AccProject.folderCrawlStatus`: 889 ok / 85 partial / 178 inaccessible
   - distinct `permType`: View Only, View+Download, Upload Only, View+Download+Upload, View+Download+Upload+Edit, Full Controller (6 tiers)
2. **Permission sliders exist** as structural dims (`dimensionCatalog.structural.ts`): `permission` (0–5), `admin`, `role`, `moduleAccess` — all always-available. The 6-tier ladder is collapsed into the single 0–5 `permission` ordinal.
3. **Taxonomy matches acc.xlsx exactly** (176/176 actions, 19/19 folder attrs, 9/9 modules, 6/6 groups — generated by `scripts/gen-acc-taxonomy.cjs`). But backing *data* is partial: only ~7 of 19 folder attributes have data in Prisma (`AccFolder.id/name/fullPath`, `AccFolderPermission.roleId/actions/permType`); the other ~12 (Size, Version, Issues, Markups, Review Status, Revision, Updated By, Version Added By, Last Updated, Inherit Permissions?, Description, Indicators) are not captured anywhere.

## User decisions (2026-05-29)

- **Folder data:** "Also collect the missing data" — but this is a separate quota-bound, multi-API ingestion milestone (**Slice D**), not part of this spec.
- **Permission tiers:** "single sliders, not a packaged slider" — split the packaged Permission control into individual per-tier sliders. Reaffirms the 2026-05-28 every-action-slider principle: no composite controls hiding detail behind one knob.
- **Polish depth:** "Professional & smooth."
- **Sequencing:** A → B → C this session; D planned separately afterward.

## Scope of THIS spec: Slices A, B, C

D (ingest the ~12 uncaptured folder attributes from Data Management item/version metadata, Issues API, Markups, Reviews/Approvals) is explicitly **out of scope** here and gets its own researched plan.

### Slice A — Polished, animated, clearly-grouped sidebar (frontend only)

**Goal:** Make the sidebar feel professional and smooth, and make the Module → Group → Action hierarchy legible at a glance.

**Tech approach:** Use existing deps only — `framer-motion@^12.38.0` (already in `package.json:103`) and the **currently-unused** motion tokens in `globals.css` (`--motion-fast: 120ms`, `--motion-normal: 200ms`, `--motion-ease: cubic-bezier(0.22,1,0.36,1)`, `--motion-slow: 480ms`). Keep the zinc dark palette (project convention: zinc not slate).

**Grouping clarity:**
- Increase nesting indentation per level (Module → Group → Action) beyond today's flat `pl-2` (`CatalogTreeSection.tsx:42,72`); add a subtle per-level **left accent rail** (`border-l`) so containment is visible.
- Module headers: full-contrast text + chevron icon (lucide-react) replacing the ambiguous `+/−` (`CatalogTreeSection.tsx:39,69`). Group headers stay muted, sentence-case.
- Sticky section headers (Structural / Activity / Folder) in `CatalogSliderSidebar.tsx` while the long list scrolls.

**Animation:**
- Expand/collapse via `AnimatePresence` + `motion.div` (height + opacity), **scoped to the toggled subtree only**. Collapsed branches remain unmounted so the full 204-dim tree never animates simultaneously. **Search-driven `forceOpen` expansion stays instant** (no animation) to avoid jank. (Performance guardrail.)
- `DimensionSlider.tsx`: thumb scales + subtle glow on hover/drag (`transition-transform` + box-shadow); range fill eases; **live value readout** updates during drag (the `SliderContext` preview push at `:271-283` already fires on change — surface its value).
- Row hover states; gentle emphasis (not pulsing) on active-filter count badges.

**Greyed rows (`DisabledRow`, `CatalogTreeSection.tsx:19-26`):** consistent muted styling + a **tooltip explaining why** the row is greyed (per-folder vs per-person, or "not collected yet"). Informative, not mysterious.

**Files:** `CatalogSliderSidebar.tsx`, `CatalogTreeSection.tsx`, `DimensionSlider.tsx` (+ possibly a small shared `motion` helper). No data/pipeline changes.

### Slice B — Un-package the Permission slider

**Goal:** Replace the single packaged **Permission level 0–5** slider with **five individual sliders**, one per real tier: View Only · View+Download · Upload · Edit · Full Controller.

**Semantics:** Each tier slider clusters nodes whose **top permission is exactly that tier** (one-hot on the already-computed `permissionStrength` 0..5). No new data required. This mirrors how `moduleAccess` (multiHot) and action dims already work.

**The overall `permission` dim** is retained **as a color option only** (color is not a slider, so it does not violate the "single sliders" principle) — useful for shading the graph by permission ceiling. *Open to dropping it entirely if the user prefers.*

**Files:** `dimensionCatalog.structural.ts` (define 5 tier dims, each `extract: f => f.permissionStrength === tierIndex ? 1 : 0`), `accTaxonomyStatic.ts` (`STRUCTURAL_DIMS` / `ACCESS_LEVELS` mapping), and remove the packaged `permission` from the slider surface (keep it on the color surface). No pipeline change.

---

### Slice C — Light up folder sliders from existing data

**Goal:** Turn the folder data we already hold into real per-person sliders, without new ingestion.

**Why not the literal 19 labels:** those are per-folder identities (a folder's name/path/size) and cannot sit on a per-(user,project) node. What *can*: aggregates over **the folders a person can reach**, via the existing join `user → role (AccDcProjectUserRole / AccProjectRole) → AccFolderPermission.roleId → AccFolder`.

**New data-backed dims (working names):**
- `folderReach` — count of distinct folders the person can access in the project (ordinal)
- `folderEditReach` — count of folders where they have Edit+ (ordinal)
- `folderControlReach` — count of folders where they are Full Controller (ordinal)

**Computation:** extend the **same graph-build aggregation that already produces `perm_strength`** (the DuckDB `graph_folder_permissions` view feeding `featureSnapshot.ts`). Aggregate at build time, never per-render. The MAX-strength join already exists; this adds COUNT-by-tier on the same join.

**The original 19 acc.xlsx folder labels** stay visible but re-tagged via Slice A's tooltip: either "per-folder — drill-down only" or "not collected yet → Slice D".

**Files:** the DuckDB folder-permission view builder (to confirm exact location during planning), `featureSnapshot.ts`, `interactionTypes.ts` (`NodeFeatureSnapshot` new numeric fields), `dimensionCatalog.folder.ts` or a new `dimensionCatalog.folderReach.ts` for the live dims.

## Testing & verification (all slices)

- **Unit:** extend catalog tests (structural/folder/actions) and snapshot tests; assert the 5 tier dims exist and one-hot correctly; assert folder-reach dims extract expected values from a fixture snapshot. Keep the existing ~1272-green suite green; `tsc` 0 errors.
- **Data verification (Slice C):** cross-check `folderReach`/`folderEditReach`/`folderControlReach` for a sample of nodes against direct DB queries before claiming done (evidence before assertion).

- **Visual:** professional & smooth; verify expand/collapse and slider drag feel are not janky with the full 204-dim tree.

## Constraints & guardrails

- **Surgical staging:** the branch carries large uncommitted WIP. Stage commits by **explicit path only**, never `-A`/`.`; check `git diff --cached --name-only` before every commit.
- **Performance:** never animate the whole tree at once; never run the folder-reach join per-render.
- **No scope creep into D:** the 19 literal folder attributes that need new ingestion stay greyed (clearly labeled) until D.
- `moduleAccess` is *not* un-packaged in this spec (out of scope; candidate for a future pass).
