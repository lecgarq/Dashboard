<objective>
Apply the DB-01 index: add a standalone `@@index([roleId])` to `AccFolderPermission` so role-leading
lookups stop paying for a full scan/`folderId`-index walk at ~6M rows, prove it with `EXPLAIN ANALYZE`,
and keep Prisma migration state consistent.

Purpose: The composite `@@unique([folderId, roleId])` cannot serve a `roleId`-leading lookup (DB-02 §1.2),
so the terrain/template queries that join `AccFolderPermission` by `roleId` (`folderPermissionTerrainView.ts`,
`templateFolderTerrain.ts`, and the `acc-hot-cache` GROUP BY) are slower than necessary. This is a live-DB
change with an environment gate, separated from the pure code/doc/test plan (09-01) per the 09-CONTEXT.md
discretion note.

Output: An updated schema, a tracked raw-SQL migration registered via `prisma migrate resolve`, an applied
live index `acc_folder_permission_role_id_idx`, an EXPLAIN ANALYZE Index-Scan witness, and a rebuilt :3000.

  raw `CREATE INDEX` (standard, NOT CONCURRENTLY) following the `prisma/migrations/...add_acc_activity_email_project_index`
  precedent, applied to the live local Postgres now, then `prisma migrate resolve --applied <migration_name>`.
  Reason: `prisma/schema.prisma` carries a pgvector `Unsupported("vector(768)")` column that makes
  `prisma migrate dev` choke. The local single-user DB tolerates the brief lock of a standard index build.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration → live Postgres | A raw `CREATE INDEX` mutates the live local DB; a wrong/duplicate index or a CONCURRENTLY failure could leave an invalid index. |
| migration state ↔ schema | If the raw SQL is applied but not registered via `migrate resolve`, Prisma migration state drifts from the DB. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-04 | Tampering | live `AccFolderPermission` index build | mitigate | `CREATE INDEX IF NOT EXISTS` is idempotent; standard (non-CONCURRENT) build is atomic on local PG, so no INVALID-index state can be left behind. |
| T-09-05 | Repudiation | Prisma migration history drift | mitigate | `prisma migrate resolve --applied` registers the raw migration; `prisma migrate status` confirms a consistent, auditable migration trail. |
| T-09-06 | Denial of Service | brief table lock during the ~6M-row index build | accept | Local single-user DB; the lock is momentary and the owner is the only consumer during the build (per the locked decision; CONCURRENTLY is the documented fallback if it ever interferes). |
</threat_model>
