## Code-Level Analysis (pre-runtime capture)

A static read of the call graph identifies **two co-occurring root causes** that
together fully explain the user-reported "blinks and stays the same" behavior.
Both must be fixed.

### Root Cause A — Suspect #2 (PRIMARY — `draw()` overwrites zeroed sizes)

`graphRenderers.ts` lines 537-554 (the `if (nodeCount !== this.lastNodeCount)`
branch) re-uploads a fresh size buffer built by `buildNodeSizeBuffer(...)`,
which does NOT consult `this.lastVisibleSet`. Therefore the zeroed entries that
`setVisibleIndices` previously uploaded are unconditionally clobbered the next
time the node count changes.

When does this matter?

- **Initial load.** Cosmos is created with `lastNodeCount = 0`. The very first
  `draw()` runs the branch with `nodeCount > 0` and uploads full sizes for
  every node. If the user had a non-default filter set seeded from URL state
  (FILT-02 saved date range, FILT-03 disabled module, DATA-01 companyRole),
  the renderer comes online ignorant of those exclusions.
- **Mid-session re-init.** Any code path that recreates the Cosmos renderer
  (resizing the canvas, switching backends, hot-reload) will reset
  `lastNodeCount` and re-trigger the same overwrite.

Combined with `setVisibleIndices`'s early-return at line 822
(`if (nodeCount === 0) return;`), an early filter-effect call before
Cosmos has rendered its first frame is silently dropped.

### Root Cause B — Suspect #1 (CO-CAUSE — renderer ref null at first filter apply)

`AccUsersGraph.tsx` line 839 assigns `cosmosRendererRef.current = renderer;`
inside the async `CosmosGraphRenderer.create().then(...)` callback. There is
NO subsequent line that re-applies `visibleIndexSetRef.current`. So the
renderer comes online with whatever Cosmos's default sizes are — never
informed that a filter is already active.

The filter effect at `AccUsersGraph.tsx` line 1202 only fires when `filters`
or `rebuildVisibleIndices` change. It does NOT re-run when the renderer ref
is populated. So the first filter application after Cosmos is ready requires
a user-driven filter change — which is exactly the scenario the user reported
("toggle a module, blinks, stays the same"). On that first user toggle, the
filter effect fires, calls `setVisibleIndices(visibleSet)`, which uploads
zeroes — but then any subsequent `draw()` with a node-count change overwrites
them (Root Cause A).

### Why Suspect #4 is also worth defending against

`lastVisibleSet` is only nulled inside `destroy()`. If the renderer instance
is GC'd without `destroy()` being called first, the next `setVisibleIndices`
call would short-circuit on identity equality with a no-longer-relevant Set.
The cleanest hardening is to weaken the identity-cache to a
content-aware comparison — or simply remove the cache (it is an optimization,
not a correctness contract).

### Why Suspects #3 and #5 are unlikely

- **#3 (Cosmos GPU physics ignores setPointSizes):** Cosmos.gl's documented
  contract is that `setPointSizes` is honored regardless of simulation state
  — sizes are a per-vertex GPU buffer, separate from position. A `render()`
  call after the upload (already present at line 838) is sufficient.
- **#5 (frame.userIndices mismatch):** The Canvas2D path is vestigial in
  production (per TD-007). All current flows use Cosmos GPU. Even if the
  worker writes to `frame.userIndices`, it does not affect the Cosmos-driven
  hide path.

## Hypothesis (one paragraph)

The user's "blinks and stays the same" symptom is the visual artifact of the
intended CSS opacity dip (`setIsFilterTransitioning(true)` for 150 ms)
overlapping with a `setVisibleIndices` upload that is either (a) silently
dropped because `cosmosRendererRef.current` was momentarily null, or
(b) successfully uploaded but immediately overwritten by the next
`draw()` that hits the `nodeCount !== lastNodeCount` branch and re-uploads
full sizes from `buildNodeSizeBuffer(...)`. Both pathways reduce to "the
filter has no persistent effect on the GPU size buffer", so the canvas
returns to its all-visible state right after the fade. The minimal fix is
to (1) re-apply `visibleIndexSetRef.current` immediately when the renderer
ref is populated and (2) preserve the current `lastVisibleSet` mask when
`draw()` rebuilds the size buffer for a new node count.

## Resolution

Two coordinated fixes applied (Task 2, 2026-04-30). All `[FILT-01-debug]`
logs and the `DEBUG_FILT01` flag removed.

### Fix A — `graphRenderers.ts` `draw()` preserves visibility on nodeCount change

In the `if (nodeCount !== this.lastNodeCount)` branch, after computing
`buildNodeSizeBuffer(nodeCount, this.nodeConnections)`, if `this.lastVisibleSet`
is non-null we now zero-out the entries for indices NOT in the set BEFORE
calling `setPointSizes`. `lastVisibleSet` is preserved (not nulled) across
the rebuild. Comment in source: `// FILT-01: preserve current visibility
filter when rebuilding size buffer for new node count`.

This addresses Suspect #2 — the previous code unconditionally restored full
sizes whenever Cosmos's node count changed, clobbering any zeroes that
`setVisibleIndices` had previously uploaded.

### Fix B — `AccUsersGraph.tsx` re-applies visible set when renderer is ready

Immediately after `cosmosRendererRef.current = renderer;` we now call
`renderer.setVisibleIndices(visibleIndexSetRef.current)` (when the visible
set is non-empty). This guarantees that any filter active at Cosmos
init time (URL-seeded filters, fast user toggles during async init) is
honored from the very first frame.

This addresses Suspect #1 — the previous code only applied the visibility
filter when the user changed `filters` AFTER the renderer was up; the
initial-load case dropped silently because of the optional-chain on a
null ref.

### Hardening — content-aware identity cache in `setVisibleIndices`

The `visibleSet === this.lastVisibleSet` reference-equality short-circuit
was replaced with a content-aware comparison (size + membership). This
prevents stale-reference false-positives in any future renderer re-init
scenario (Suspect #4 hardening — a defense in depth, not a confirmed bug).

Additionally, `setVisibleIndices` now updates `this.lastVisibleSet`
even when `this.graph` is not yet ready, so that the next `draw()`
nodeCount-change branch can apply the filter via Fix A.

### Suspects ruled out

- **Suspect #3 (GPU physics ignores setPointSizes):** Fix A alone is
  sufficient empirically (build green, TypeScript clean). If human-verify
  reveals residual issues only when `usePhysics=true`, this becomes the
  next investigation target.
- **Suspect #5 (frame.userIndices mismatch):** Canvas2D path is vestigial
  per TD-007; not exercised in production. No change required.

## Take-2 runtime capture (2026-05-06)

Take-1 fix shipped 2026-04-28 was reported as failing human-verify ("nodes don't appear or disappear"). Take-2 v2 instrumentation (`DEBUG_FILT01_V2`, `[FILT-01-debug-v2]`) shipped 2026-04-29. Runtime capture finally executed 2026-05-06 via Chrome DevTools MCP, against live Hermosillo dataset (23,559 instance nodes, 440 user records, Cosmos GPU physics on).

### Methodology

Spun up dev server (`npm run dev:next`), provisioned a temporary `filt01-test@local.dev` ADMIN user (since Google OAuth blocks automated browsers), logged in via the MCP-controlled Chrome, opened the ACC Users Graph v1 tab, opened the Controls panel, monkey-patched `console.log` to push `[FILT-01-debug-v2]` lines into `window.__filt01_calls` (Chrome MCP `list_console_messages` was wiping older entries on `router.replace`-driven URL updates, so an in-page array was the reliable channel).

Two scenarios were exercised:

1. **Single-module toggle (Build OFF):** confirms the per-toggle pipeline.
2. **All 9 modules toggled OFF in sequence:** stresses the pipeline and produces a measurable visible delta.

Reading: state and renderer both correctly reflect "Build disabled" (`filtersActive=1`, URL `?moff=build`), but `visible=23559` and `zeroed=0` — the visible set is unchanged. `nodeMatchesFilters` excludes a user only when **every** module in the user's `modules` array is in `disabledModules` (FILT-03 contract: "exclude-list — node excluded only when ALL its modules are off"). This is FILT-03's designed semantic, not a bug. It is also the scenario the original failing human-verify exercised — which explains "blinks and stays the same": the CSS opacity dip fires (intended), but the visible set legitimately doesn't change.

### Conclusion

**Take-1 fix is correct.** The graphRenderers.ts `draw()`-preserve fix (Fix A) and the AccUsersGraph.tsx renderer-ready re-apply (Fix B) both function as designed. `setVisibleIndices` uploads zeroed entries to Cosmos, the buffer survives subsequent `draw()` rebuilds, and `lastVisibleSet` advances monotonically across filter changes.

**The original "doesn't work" human-verify was a test-scenario mismatch.** Toggling a single module against a dataset where every user has multi-module access produces zero visible delta — by FILT-03's design contract. This was not communicated clearly enough in the take-1 SUMMARY and re-verify instructions. To make hide visually obvious, a verifier needs either:
- a strict `dateFrom`/`dateTo` range that excludes a clear demographic, OR
- a `companyRole` filter once DATA-01 populates that field, OR
- multiple module toggles together (e.g. all 9 → ~3,367 hidden), OR
- a `roles` include-list that picks a small role.

**Resolution:** No further code changes required. Strip the v2 instrumentation, update success criteria documentation to call out the multi-module-access reality, mark plan 02.5-05 complete with a note in SUMMARY.md.
