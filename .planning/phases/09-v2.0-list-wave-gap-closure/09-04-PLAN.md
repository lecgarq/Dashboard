**API:**
```typescript
export function useVisibleRowEmails(): {
  visibleEmails: string[];                              // sorted ascending, deduped, lowercased
  registerRow: (email: string) => (el: HTMLElement | null) => void;
};
```

**Behavior:**
- One stable `IntersectionObserver` instance per hook invocation, memoized via `useRef` + lazy init.
- `rootMargin: "200px"` (RESEARCH lock).
- Internal `Map<HTMLElement, string>` keyed by DOM node → email.
- `registerRow(email)` returns a React ref callback. When called with an element, it observes that node and records the mapping. When called with `null`, it unobserves and deletes the entry. Cleanup on unmount disconnects the observer.
- Visible set rebuilt via the observer callback. Batch updates inside `requestAnimationFrame` (Pitfall 5: coalesce to avoid storms during scroll). Store visible Set in `useState<string[]>([])`.
- Returns a stable identity for `registerRow` via `useCallback`.

**Edge cases:**
- Email may be empty / non-email-shaped (defensive — never store empties).
- Same email registered for two row instances (re-render) — store latest element; both observer-callbacks resolve to the same email so duplication is naturally handled by Set semantics.

**Vitest** (jsdom env — `vitest.config.ts` already supports DOM tests per the file list):
- Mock `IntersectionObserver` globally (`vi.stubGlobal('IntersectionObserver', ...)` with a manual implementation that exposes `.simulate(entries)`).
- Test 1: register 3 emails, simulate 2 intersecting → `visibleEmails` contains those 2.
- Test 2: ref callback called with `null` → email removed from visible set on next intersection event.
- Test 3: re-register same email with new element → no duplicates in visibleEmails.
- Test 4: unmount → observer.disconnect() called once.
- Test 5: rapid-fire intersection callbacks coalesce via rAF — visibleEmails updates ≤ once per frame (mock `requestAnimationFrame`).

Pure hook — no Prisma, no tRPC.

**Spinner during sort fetch** (CONTEXT lock):

**Row reordering pipeline:**
- Flatten `sortInfiniteQuery.data?.pages.flatMap(p => p.rows)` → `orderedEmails: string[]` (lowercased).
- The current pipeline computes `displayRows = filteredRows` (or similar). When `activitySort.active`, replace with:
  ```typescript
  const displayRows = useMemo(() => {
    if (!activitySort.active) return filteredRows;
    const orderMap = new Map(orderedEmails.map((e, i) => [e, i]));
    const inSort: typeof filteredRows = [];
    const remainder: typeof filteredRows = [];
    for (const row of filteredRows) {
      if (orderMap.has(row.email.toLowerCase())) inSort.push(row);
      else remainder.push(row);
    }
    inSort.sort((a, b) => (orderMap.get(a.email.toLowerCase())! - orderMap.get(b.email.toLowerCase())!));
    // RESEARCH Open Question 3: append no-activity rows in alphabetical order, always last regardless of asc/desc
    remainder.sort((a, b) => a.email.localeCompare(b.email));
    return [...inSort, ...remainder];
  }, [activitySort.active, orderedEmails, filteredRows]);
  ```
- The virtualizer consumes `displayRows` directly — no other changes to virtualization required.

**Empty-row sort position (CONTEXT discretion → "always last regardless of asc/desc"):** handled by the remainder concat above; the server query already does `NULLS LAST` for users whose `MAX(createdAt)` is NULL among the sorted set; the client append handles users with zero file activity at all.

**Cross-task contract:** Task 2's batch query continues to feed cell values. When `activitySort.active` toggles, the new row order changes which rows are virtualized, which changes `visibleEmails`, which re-fires the batch query naturally. No coordination needed between the two queries.

**Header arrow / spinner accessibility:** The sort `<button>` carries `aria-label={"Sort by last file activity, " + (activitySort.active ? activitySort.direction : "inactive")}`. Spinner is decorative (`aria-hidden`).
