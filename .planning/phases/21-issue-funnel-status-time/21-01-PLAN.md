`loadIssueFunnel(force = false)`. Implementation:

- `import "server-only"`, `import { db } from "@/server/db"`, and
  `import { buildProjectNameMap, resolveProjectName } from "./folderActivityView"`.
- Module-level 5-min TTL cache with `force` bypass — mirror `coordinationByProjectView.ts`
  lines 37-43 exactly.
- One `Promise.all` with four entries:
  1. Month cut (raw SQL — mirror `activityTimelineView.ts`'s date_trunc groupBy shape):
     ```sql
     SELECT "projectId",
            to_char(date_trunc('month', "createdAt"), 'YYYY-MM') AS month,
            COUNT(*)::int AS count
     FROM "AccIssue"
     WHERE "createdAt" IS NOT NULL
     GROUP BY "projectId", month
     ```
     via `db.$queryRaw<...>` with a raw-row interface `{ projectId: string; month: string; count: number }`.
     The `WHERE "createdAt" IS NOT NULL` is REQUIRED — `AccIssue.createdAt` is `DateTime?`
     and a null would produce a corrupt month key (RESEARCH Pitfall 3).
  2. Status cut: `db.accIssue.groupBy({ by: ["projectId", "status"], _count: { id: true } })`
     — same call as `coordinationByProjectView.ts` line 46-50 but WITHOUT the
     `where: { isCoordination: true }` clause (full 17,360-issue set is the phase boundary)
     and WITHOUT any createdAt filter (a null-createdAt issue still has a valid status and
     must count in the donut).
  3. `db.accProject.findMany({ select: { id: true, name: true } })`
  4. `db.accDcProject.findMany({ select: { id: true, name: true } })`
- Build `nameById` via `buildProjectNameMap(projects, dcProjects)` once; map both row sets
  through `resolveProjectName(nameById, projectId)` into `IssueFunnelMonthRow[]` /
  `IssueFunnelStatusRow[]`. For the status cut, coalesce `g.status ?? "unknown"` (the
  `coordinationByProjectView.ts` line 75 convention — never drop a null status).
- Do NOT filter on `deleted` (no existing AccIssue consumer does; introducing that decision
  here alone would silently diverge from the verified 17,360 figure — RESEARCH Open Q3).
