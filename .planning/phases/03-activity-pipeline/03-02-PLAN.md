export type ActivityCategory = "view" | "upload" | "edit" | "delete" | "memberEvent" | "projectEvent" | "other";

const MAP: Record<string, ActivityCategory> = {
  "File Viewed": "view",
  "Document Viewed": "view",
  "File Downloaded": "view",
  "File Uploaded": "upload",
  "Document Version Created": "upload",
  "File Edited": "edit",
  "Markup Created": "edit",
  "Comment Added": "edit",
  "File Deleted": "delete",
  "File Restored": "delete",
  "Member Added": "memberEvent",
  "User Invited": "memberEvent",
  "Project Member Added": "memberEvent",
  "Project Created": "projectEvent",
  "Project Updated": "projectEvent",
};

export function categorize(rawAction: string): ActivityCategory {
  return MAP[rawAction] ?? "other";
}

export const FILE_CATEGORIES: ReadonlySet<ActivityCategory> = new Set(["view", "upload", "edit", "delete"]);
export const INVITATION_ACTIONS: ReadonlySet<string> = new Set(["Member Added", "User Invited", "Project Member Added"]);

  <action>Create the second-stage cron entry point. Pattern: same structure as `scripts/deep-sync.cjs` (dotenv, PrismaClient with `max: 2`, dynamic `tsx`-style require for the lib helper).

Behavior:
1. Load .env, instantiate PrismaClient.
2. Find AccDataConnectorJob rows where `status IN ('pending', 'running')` AND `ingestStartedAt IS NULL` (if Plan 01 added the column — if not, use `status='pending'` as the gate). Skip if zero candidates.
3. For each candidate (process sequentially — no parallelism across jobs to avoid memory pressure per RESEARCH Pitfall 3):
   a. Poll APS GET `/data-management/data-exchange/v1/requests/{requestId}/jobs` using `fetchWithRetry` from `lib/server/acc-admin.ts`.
   b. If APS reports `status === "success"` → extract `downloadUrl`; mark the row `running` with `ingestStartedAt = now()`; call `ingestActivityZip(downloadUrl, prisma, job.id)`; mark `success` with `completedAt = now()` and persist `rowsByFile` summary to a JSON column or to `SyncMeta('deep')` notes.
   c. If APS reports `failed` or `cancelled` → mark `failed`, capture error, optionally send Resend email (reuse SYNC-04 email helper if present; if not, log only — UI plan handles surfacing).
   d. If `pending` or `running` → leave the row alone; next cron tick re-polls.
4. Handle 403 on signed URL by re-polling APS once for a fresh URL (RESEARCH Pitfall 2).
5. Always `await prisma.$disconnect()` at end.

Cadence: Designed to be run by Railway cron every 30min (operator wires the cron job; this script just needs to be safe to run repeatedly).

Overlap guard: At process start, check if another ingest run is concurrent via a row-level lock or a sentinel `SyncMeta('deep_ingest_lock')`. Simplest: skip any job already in `running` state with `ingestStartedAt` within the last 60min (assume stuck or in-flight). Document the chosen lock strategy in the SUMMARY.

Exit code 0 on success (including "no jobs to process"), exit 1 on unhandled error.

Verification harness: Add a `--dry-run` flag that polls and logs decisions but does not run ingest. Used in the verify step.</action>

**server/routers/acc-activity.ts** — implement THREE procedures:

1. `getFileActivityForUser({email})` (ACTV-03):
   - Input: `z.object({ email: z.string().email() })`.
   - Lowercase the email server-side.
   - Strategy: 4 parallel `findFirst` queries — one per file category — each `WHERE userEmail = ? AND rawAction IN (<category's raw strings>) ORDER BY createdAt DESC LIMIT 1`. Build the IN-list from `activityCategories.ts` (export reverse maps for view/upload/edit/delete).
   - Return: `{ lastView: Date|null, lastUpload: Date|null, lastEdit: Date|null, lastDelete: Date|null }`.
   - Rationale: 4 indexed lookups (userEmail, createdAt DESC) are faster than the take:200 approach in RESEARCH Example 1 and don't risk missing categories below the top-200 cutoff.

2. `listForUser({email, categories?, projectId?, dateRange?, cursor?, limit})` (ACTV-05):
   - Input: per RESEARCH Example 1 (validate with zod).
   - Lowercase email server-side.
   - Where clause: `userEmail = ?`, optional `projectId = ?`, optional `createdAt BETWEEN ? AND ?`.
   - If `categories` provided, expand to raw action IN-list via `activityCategories.ts` reverse map.
   - Order: `createdAt DESC, id DESC`. Cursor pagination: `WHERE (createdAt, id) < (cursor.createdAt, cursor.id)`. Limit + 1 to compute hasMore.
   - Return: `{ rows: AccActivity[], nextCursor: {createdAt, id} | null }`.
   - Performance: this drives the side-panel drill-down; must complete < 200ms with ~1M rows assuming (userEmail, createdAt DESC) index used.

3. `listInvitations({windowDays, inviterFilter?})` (ACTV-04 backend):
   - Input: `z.object({ windowDays: z.union([z.literal(7), z.literal(30), z.literal(90)]).default(30), inviterFilter: z.string().optional() })`.
   - Where: `rawAction IN ('Member Added','User Invited','Project Member Added')` AND `createdAt >= now() - windowDays*1d`.
   - If `inviterFilter` provided (autodeskId): also filter `autodeskId = inviterFilter` AND drop the date window (CONTEXT.md: "When 'Filtered by Jane' is active, time-window filter is relaxed").
   - Order: createdAt DESC.
   - For each row, do the attribution join: parse email from `details`, lookup invitee in AccProjectMember (case-insensitive), lookup inviter in AccProjectMember by `autodeskId`. Build response: `{ inviteeEmail, inviteeName, inviteeAvatarUrl, inviterAutodeskId, inviterName, inviterAvatarUrl, createdAt, projectId }`. Use a single batch `findMany` to look up both invitee + inviter members for the page (avoid N+1).
   - Re-invited users (multiple inviters for same invitee): group by `inviteeEmail` in the result and return `{ primaryInviter, otherInviters: [...] }` per CONTEXT.md "+N others" requirement.
   - Limit: 100 rows per call (widget pulls top 10; "See all" pulls full window — operator can raise later).

Use `protectedProcedure` from existing trpc context (mirror `server/routers/acc-sync.ts`). Use `ctx.db` (or `ctx.prisma` — match existing pattern).
