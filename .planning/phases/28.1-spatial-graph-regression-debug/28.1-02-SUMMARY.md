## Root cause (systematic-debugging — CONFIRMED before the effective fix)

The `/users/spatial-graph` route **prefetches `bulkUsers`+`instanceEmbedding` server-side** with
inputs matching the shell query exactly (`acc-route-hydration.ts:55-61`), wrapped in a page-level
`<HydrationBoundary>`. Yet the client re-fetched both on every load (~2.3 s, blocking). SSR-HTML
inspection (20 MB, authenticated fetch) proved the dehydrated payload **was present and
`status:"success"`** with **correct, matching query hashes** — so it was not an auth-gate, a key
mismatch, or a prefetch failure.

The tell was the payload's top-level `meta.values` keyed by `queries.0.state.data.0.…`:
`createServerSideHelpers({ transformer: superjson }).dehydrate()` serializes the **whole**
dehydrated state with superjson (returning `{ json, meta }` — a Pages-Router idiom where
`withTRPC` deserializes it on the client). In the App Router the page passed that wrapper
**straight to `<HydrationBoundary state={…}>`**, which expects a **raw `DehydratedState`**
(`{ mutations, queries }`). With no top-level `queries`, the boundary hydrated **nothing** and the
shell's `useQuery` fetched fresh. Only observable here because `bulkUsers` is the one heavy
prefetched query actually consumed on this route.

### First fix attempt (reverted — insufficient)

Adding `dehydrate.serializeData`/`hydrate.deserializeData` (superjson) to the client `QueryClient`
(`lib/core/providers.tsx`, the documented tRPC-v11 factory option) did **not** eliminate the
refetch — verified empirically (`bulkUsers` still fetched, dur ~1952 ms, blocking). Those options
run **per-query** during hydration, but the boundary never received valid per-query data to run
them on (the whole state was one `{ json, meta }` blob). Reverted to net-zero.

## Fix (narrowest effective boundary — the page)

`app/(dashboard)/users/spatial-graph/page.tsx`: deserialize the transformer-wrapped state before
the boundary — `superjson.deserialize(helpers.dehydrate())` — guarded on the `{ json }` wrapper so
a raw `DehydratedState` passes through untouched. The boundary now receives a real
`DehydratedState`, hydrates `bulkUsers`+`instanceEmbedding`, and the shell's `useQuery` finds fresh
data on mount — **no client refetch**. The deserialized state (Dates/undefined) re-crosses the RSC
boundary via Next Flight, which natively handles those types. Scoped to this one route (the
`access-analysis` sibling only redirects here), so zero blast radius on other routes.

## Deviations

- Plan Task 2 anticipated the fix would likely land in `AccessAnalysisShell.tsx` (idle-schedule /
  memoize / lazy the build path). Source evidence overturned that: the build path is 317 ms and
  the real cost was an SSR-hydration miss in the route's page component. Fixed there instead — a
  trivial, in-scope correction recorded here per the plan's "make a trivial correction and record
  it" rule. No data source, loader, Prisma table, or npm dependency touched; cosmos.gl stays 3.3.0.
- The regression is **not** intrinsic to the widened v2.4 surface (build = 317 ms). The fixed
  hydration miss is **pre-existing** ("hydration-key mismatch", `project_spatial_graph_load_speed`)
  — fixing it drove the absolute number well under the gate, which is the owner-chosen outcome.
