## Summary

All three items are additive, small-surface changes confined to the `/access-analysis` Overview
tab, and every data source they need already exists in the Prisma DB and is already loaded (in
whole or in the exact shape needed) by the current Overview code path. There is **no tRPC
involved anywhere in this tab** — the established pattern is `lib/server/<name>View.ts` (cached
loader) → pure `app/(dashboard)/access-analysis/<name>Counts.ts` transform (co-located Vitest) →
`"use client"` chart under `components/` → wired into `mainCharts.tsx` (RSC) /
`AccessAnalysisCharts.tsx` (client shell) → mounted in `OverviewTabPanel.tsx`.

Two of CONTEXT.md's VERIFY items resolved with **evidence that changes the plan's risk profile**
from what CONTEXT.md assumed:

1. **Item 1's "proven path" is not quite what CONTEXT.md says.** `accessInstanceView.ts:107`'s
   `reduceModules()` call does NOT consume `AccProjectMember.products` — it consumes
   `AccDcProjectUserProduct` (the DC snapshot's per-user-per-product row table), fed by a
   `findMany` on that table in `loadInstanceView()`. `AccProjectMember.products` (the live-API
   JSON blob CONTEXT.md names) is consumed by a **different, narrower** code path:
   `server/routers/acc-members.ts`'s `getProductsForUser` procedure (single-user, lazy) and the
   pure JSON parser `lib/acc/productsTierMap.ts`. Both shapes satisfy `reduceModules`'s input
   type (`Array<{productKey, accessLevel}>`), so `reduceModules` itself is reusable either way —
   but the **coverage** differs materially: `AccDcProjectUserProduct` is scoped to DC-ingested
   projects only (memory: 428–550/1,153 projects), while `AccProjectMember` is the live-API
   membership table covering the full live project set (14,566 rows, all 1,153 `AccProject`
   rows reachable). See "Item 1" below for the concrete recommendation.

2. **Item 2's "service-first fix" will move far fewer rows than the framing implies, and the
   headline "~966 Model Coordination misattribution" figure is already fixed in current code —
   it is not live evidence for this phase.** Live cross-tabs run against both activity tables
   during this research pass show:
   - `AccActivityAccds` (the **dominant** source — accds-primary in the unified merge, ~93%+ of
     shipped rows): `serviceGroup` is **100% populated**, only 4 distinct values
     (`docs`/`issues`/`sheets`/`admin`), and already agrees with `classifyActivity`'s verb-based
     module assignment on >99.7% of rows. Real disagreement is tiny: ~186 rows (0.004%) land in
     `Unmapped`, and ~8,107 `docs`-serviceGroup rows are deliberately reclassified to "Admin
     Actions" by an intentional verb override (permission/membership actions), not a bug.
   - `AccActivity` (DC batch, the **secondary/backfill** source, ~1.1M rows): `service` is
     ~42.1% populated (471,906 / 1,120,388 non-null this pass — consistent with the ~40.7%
     figure in memory), with 7 distinct values (`docs`/`sheets`/`bridge`/`issues`/`submittals`/
     `rfis`/`admin`). Real disagreement here is ~8,575 rows (~1.8% of populated-service rows),
     concentrated in Design-Collaboration↔Data-Management sheet/docs boundary calls and
     docs↔Admin-Actions permission-verb overrides — **not** Model Coordination.
   - The `docs/activity-module-audit.md` file quoting "Model Coordination — 966 activities" is
     **stale** (untracked, never regenerated) and predates commit `6164cfae` (2026-06-05,
     "reroute phantom Model-Coordination verbs out of the activity donut"). Live queries this
     pass confirm **zero** `issues`-service rows disagree with the current Build assignment in
     either table — that specific complaint is already resolved. Treat this doc as superseded;
     do not cite its numbers as current evidence.
   - **Consequence for planning:** a literal "service string maps 1:1 onto our 10-module

     correct and cheap to implement, but the planner should scope the caveat copy and owner

### Pattern: donut drill via local component state (NOT the `sliceFilters` cross-filter bus)

CONTEXT.md locks "click-to-drill" for both new panels using "existing drill-list conventions."
Two drill conventions coexist in this codebase and the choice matters:

1. **Local-drill-state donuts** (`ModulesPieChart.tsx`'s `toggleDrill`, `IssueStatusChart.tsx`,
   `RolesPieChart.tsx`'s expand-in-place) — a `useState<string|null>` toggled on slice/legend

2. **Cross-filter-bus donuts** (`ActivityByRolePieChart.tsx`/`CompaniesActivityPieChart.tsx`) —
   emit `onSliceClick` writing into the shared `sliceFilters` bus, which `applySliceFilters`
   narrows other panels by.

CONTEXT.md's "Provisioned modules... click a bar → drill list of top projects for that module"
and "Activity share by project... click a project slice → that project's module breakdown" both
describe **local, panel-owned drill state** (pattern 1) — matching `ModulesPieChart.tsx` (the
donut directly above the new panels) and `IssueStatusChart.tsx` (the most recently shipped
sibling, Phase 21). **Do not wire either new panel into the `sliceFilters` bus** — CONTEXT.md
never asks for cross-filtering, and Phase 21's `IssueStatusChart.tsx` deliberately grep-verified
its own absence of `onSliceClick`/`activeSlice` for the same reason.

## Item 1: Provisioned-modules chart — data source recommendation

**Recommendation: build `provisionedModulesView.ts` over `AccProjectMember`, not
`AccDcProjectUserProduct`.**

`AccProjectMember` (455-477 in `prisma/schema.prisma`) is the live-API membership table: 14,566
rows (per STATE.md census), one row per `(projectId, autodeskId)`, carrying `products: Json` (a
per-module tier map, e.g. `{"docs":"member","build":"administrator"}` — confirmed shape via
`lib/acc/productsTierMap.ts`'s `ProductsSchema = z.record(z.string(), z.union([TierEnum,
z.string()]))`). It is reachable for the **full** live `AccProject` set (1,153 projects), unlike
`AccDcProjectUserProduct` which is scoped to whatever subset Data Connector has ingested
(~428–550/1,153 projects per memory `project_dc_access_universe.md`).

`accessInstanceView.ts`'s existing `reduceModules()` call already proves the parsing logic
(`KEY_TO_ID` module-key normalization + `hasAccess`/`isAdminLevel` tier checks) works correctly
for `{productKey, accessLevel}` pairs regardless of source table — reuse `reduceModules` itself
(`app/(dashboard)/access-analysis/modules.ts:33`) unchanged, just feed it JSON-derived pairs
instead of `AccDcProjectUserProduct` rows:

```typescript
// lib/server/provisionedModulesView.ts — NEW, mirrors accessInstanceView.ts's shape/caching
import "server-only";
import { db } from "@/server/db";
import { reduceModules } from "@/app/(dashboard)/access-analysis/modules";
import { buildProjectNameMap, resolveProjectName } from "./folderActivityView";

export interface ProvisionedModuleRow {
  projectId: string;
  projectName: string;
  moduleId: string; // one row per (member, module) grant — pre-classified, ready to groupBy
}

let cache: { at: number; rows: ProvisionedModuleRow[] } | null = null;
const TTL_MS = 5 * 60 * 1000;

export async function loadProvisionedModules(force = false): Promise<ProvisionedModuleRow[]> {
  if (!force && cache && Date.now() - cache.at < TTL_MS) return cache.rows;
  const [members, liveProjects, dcProjects] = await Promise.all([
    db.accProjectMember.findMany({ select: { projectId: true, products: true } }), // 14,566 rows — small, bounded (same scale as accessInstanceView.ts's existing findMany calls)
    db.accProject.findMany({ select: { id: true, name: true } }),
    db.accDcProject.findMany({ select: { id: true, name: true } }),
  ]);
  const nameById = buildProjectNameMap(liveProjects, dcProjects);
  const rows: ProvisionedModuleRow[] = [];
  for (const m of members) {
    // products is a Json blob { [productKey]: accessLevel } — adapt to reduceModules's
    // Array<{productKey, accessLevel}> input (same Object.entries shape as
    // lib/acc/quick-sync-extraction.ts:801's existing pp.products handling).
    const pairs = Object.entries((m.products ?? {}) as Record<string, string>)
      .map(([productKey, accessLevel]) => ({ productKey, accessLevel }));
    const { modules } = reduceModules(pairs);
    for (const moduleId of modules) {
      rows.push({ projectId: m.projectId, projectName: resolveProjectName(nameById, m.projectId), moduleId });
    }
  }
  cache = { at: Date.now(), rows };
  return rows;
}
```

This is a `findMany` (14,566 rows) + JS reduce — **not** the OOM-class guardrail violation the
STATE.md fan-out note warns about (that guardrail targets `AccActivity`/`AccActivityAccds`/
`AccFolder`/`AccFolderPermission`-scale tables, millions of rows). `accessInstanceView.ts` already
does the equivalent (multiple `findMany` calls + JS `Map`-based reduction) for this exact
Roles/Modules domain — this loader is precedented, not novel risk.

**Pure transform** (`provisionedModulesCounts.ts`, mirrors `moduleCounts.ts`'s `summarizeModules`
shape but grouping already-classified `ProvisionedModuleRow[]` by `moduleId` instead of
classifying `rawAction` strings):

```typescript
export interface ProvisionedModuleBar { id: string; name: string; value: number; } // grant count
export interface ProvisionedModuleSummary {
  bars: ProvisionedModuleBar[];           // sorted desc, horizontal-bar order
  total: number;
  projectsByModule: Map<string, Array<{ projectId: string; projectName: string; count: number }>>; // drill payload
}
export function summarizeProvisionedModules(rows: ReadonlyArray<ProvisionedModuleRow>): ProvisionedModuleSummary { /* groupBy moduleId, then by projectId within each module for the drill */ }
```

**Coverage labeling:** since `AccProjectMember` is the live-API superset, coverage is
effectively 100% of the live project set for members who have synced `products` — no
DC-subset caveat is needed for this chart specifically (unlike the Roles donut, which is
`AccDcProjectUser`/`AccDcProjectUserProduct`-scoped and therefore DOES carry the DC-coverage
caption). **VERIFY at plan time:** confirm no `AccProjectMember` rows have `products = null` or
malformed JSON in a way that would silently zero out a project — `parseProductsJson`'s
`ProductsSchema.safeParse` already returns `[]` on failure (never throws), so worst case is an
undercount, not a crash; still worth a quick live count of `products IS NULL` rows for the
caption if any exist.

### The union that must change: `moduleActivityView.ts` drops service data today

`lib/server/moduleActivityView.ts`'s `loadModuleActivity()` raw SQL union (lines 40-65) selects
only `projectId`, `rawAction` (aliased from `activityVerb` for the accds branch), and `count` —
**it never selects `service` or `serviceGroup` from either table.** This means the merged
`ModuleActivityRow[]` shipped to the client today carries **zero** service information, so
`summarizeModules` has no way to be service-aware without this SQL changing first.

```sql
-- CURRENT (lib/server/moduleActivityView.ts, verified lines 40-65) — service/serviceGroup absent
SELECT "projectId" AS pid, "activityVerb" AS action, COUNT(*)::int AS c
  FROM "AccActivityAccds" GROUP BY 1, 2
UNION ALL
SELECT COALESCE(NULLIF(d."projectId", ''), '') AS pid, d."rawAction" AS action, COUNT(*)::int AS c
  FROM "AccActivity" d LEFT JOIN astart a ON a."projectId" = d."projectId"
  WHERE ... GROUP BY 1, 2
```

**Required change:** add `serviceGroup`/`service` to both `GROUP BY`/`SELECT` lists (they become
part of the grouping key, since attribution must be per-(project, action, service) tuple, not
just per-(project, action)):

```sql
-- RECOMMENDED shape — grandTotal row count stays bounded (still ~2-3k rows -> maybe ~3-5k with
-- the extra grouping dimension, since accds only has 4 serviceGroup values and AccActivity has 7)
SELECT pid, action, service, SUM(c)::int AS count FROM (
  SELECT "projectId" AS pid, "activityVerb" AS action, "serviceGroup" AS service, COUNT(*)::int AS c
    FROM "AccActivityAccds" GROUP BY 1, 2, 3
  UNION ALL
  SELECT COALESCE(NULLIF(d."projectId",''), '') AS pid, d."rawAction" AS action, d."service" AS service, COUNT(*)::int AS c
    FROM "AccActivity" d LEFT JOIN astart a ON a."projectId" = d."projectId" WHERE ... GROUP BY 1, 2, 3
) u GROUP BY pid, action, service
```

`ModuleActivityRow` (`lib/acc/moduleCountsTypes.ts`) gains an optional `service?: string | null`
field — a backward-compatible, additive change (existing test fixtures that omit `service`
should still type-check if the field is optional, but **verify** — `moduleCounts.test.ts`'s `mk()`
helper constructs `ModuleActivityRow` literals and will need a `service` arg added or defaulted).

### Service-first precedence layering (where to put the new logic)

Given `classifyActivity` is a pure `(rawAction: string) => {moduleId,label,category}` function
with exactly one production caller, the cleanest layering (least churn, keeps
`classifyActivity`'s existing signature and its own unit tests intact) is:

1. **Extend `classifyActivity`'s signature** to accept an optional second parameter:
   `classifyActivity(rawAction: string, service?: string | null)`. When `service` is
   non-null/non-empty, consult a new small `SERVICE_TO_MODULE` precedence table (the researched
   4-7 value map already prototyped in `scripts/diag-activity-service-xtab.cjs`/
   `diag-activity-module-audit.cjs` — `docs/sheets/bridge → dataManagement`, `issues/submittals/
   rfis → build`, `admin → adminActions`) **only for the handful of modules it can actually
   speak to**; when service doesn't resolve to a module (any other/unrecognized value, or when
   the resulting override would collapse today's more granular verb-based split — see the
   "docs → Design Collaboration/Datum/Admin Actions" cases quantified above), **fall through to
   the existing verb-based logic unchanged.** This keeps 100% of the existing test suite
   (`activityClassification.test.ts`) passing unmodified for the `service` omitted case (default
   `undefined` behaves exactly as today) and only adds new test cases for the `service`-present
   branch.
2. `summarizeModules` (`moduleCounts.ts`) passes `row.service` through to `classifyActivity`, and
   additionally accumulates two running counters (`serviceAttributed`, `verbInferred`) for the
   caveat's live split.
3. **Do not** implement this at the `moduleOverrides.ts` barrel layer — it is a 4-line re-export
   with no logic (10-VERIFICATION.md confirms this explicitly); adding logic there would break
   the Phase 10 BND-02 layering decision that moved all classification logic into
   `lib/acc/activityClassification.ts`.

## Common Pitfalls

### Pitfall 1: Treating `docs/activity-module-audit.md`'s "Model Coordination — 966" figure as current
**What goes wrong:** Planning the item-2 fix around a "big Model Coordination misattribution"
story that live data no longer supports.
**Why it happens:** The file is untracked, was generated once, and was never regenerated after
commit `6164cfae` (2026-06-05) redirected all `issue-*` verbs to Build and excluded Model
Coordination from the donut entirely.
**How to avoid:** Regenerate the audit (or run the two diagnostic scripts fresh) as part of this
phase's before/after evidence step; do not cite the existing file's numbers in the plan, caveat
copy, or checkpoint materials.
**Warning signs:** Any plan draft that says "reconciles Model Coordination attribution" as the
headline outcome of item 2 — the live evidence says the actual movement is in Design
Collaboration/Admin Actions/Data Management boundaries, not Model Coordination.

### Pitfall 2: Assuming `service`/`serviceGroup` can fully replace `classifyActivity`
**What goes wrong:** Designing a `SERVICE_TO_MODULE` table as the primary classifier, expecting
it to cover all 10 donut modules.
**Why it happens:** "Service-first" sounds like a full replacement.
**How to avoid:** `serviceGroup` has only 4 values, `service` has 7 — neither can independently
resolve Preconstruction, Cost Management, Design/Forma, AutoSpecs, Datum, or (correctly) Model
Coordination-redirect-to-Build/Data-Management nuances. Keep `classifyActivity`'s verb logic as
the base; layer service as a **narrow override** only where it resolves unambiguously and
disagrees, per the measured ~1-2% disagreement rate.
**Warning signs:** A plan that proposes deleting or radically simplifying
`lib/acc/activityClassification.ts`'s excel-taxonomy logic.

### Pitfall 3: Conflating `AccProjectMember.products` with `AccDcProjectUserProduct`
**What goes wrong:** Building item 1's loader against `AccDcProjectUserProduct` because
CONTEXT.md says "the same source `accessInstanceView.ts` uses," inheriting the DC-only project
coverage gap (~428-550/1,153) instead of the fuller live coverage `AccProjectMember` offers.
**Why it happens:** `accessInstanceView.ts:107`'s call to `reduceModules()` reads like it's
consuming `AccProjectMember.products` at a glance; it's actually fed by a different upstream
`findMany` (`AccDcProjectUserProduct`).
**How to avoid:** Read `accessInstanceView.ts`'s `loadInstanceView()` function (lines 129-152)
directly — `raw.products` traces to `db.accDcProjectUserProduct.findMany(...)`, not
`AccProjectMember`. Build the new loader against `AccProjectMember` directly (see Item 1 code
above) for materially better coverage.
**Warning signs:** A provisioned-modules chart whose project picker options are visibly narrower
than the Activity-by-module donut's (956 accds-covered projects) or the Roles donut's (~550
DC-covered) — if the new chart's coverage looks smaller than expected, check which product table
it actually queries.

### Pitfall 4: Growing `moduleActivityView.ts`'s SQL union without re-verifying row-count bound
**What goes wrong:** Adding `service`/`serviceGroup` to the `GROUP BY` clause could multiply the
merged row count (today ~2-3k rows) if `service` values fan out per `(project, action)` pair.
**Why it happens:** More grouping dimensions = more groups, in the worst case.
**How to avoid:** Bound is still small in practice — `AccActivityAccds` has only 4 serviceGroup
values and `AccActivity` has 7, so the worst-case multiplier is ~4-7x on a ~2-3k-row result
(~10-20k rows), still far below the OOM-guard threshold this codebase cares about (millions of
rows). Confirm the actual post-change row count with a quick `SELECT COUNT(*) FROM (...) u`
smoke test before wiring the client, and keep the aggregate-bound Vitest test's row-count
assertion (research question 7) in sync with whatever the real number turns out to be.
**Warning signs:** `loadModuleActivity()`'s payload comment ("~2-3k rows (~200 KB)") becoming
stale after this change — update the comment alongside the SQL.
