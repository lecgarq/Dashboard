## Interpretation

Movement is real but small (order of 0.0040% of total activity). The
live movement matrix above shows the actual shape of this run, not a hypothetical:
- **Unmapped -> Build**: 126 rows (0.0027%).
- **Unmapped -> Data Management**: 41 rows (0.0009%).
- **Data Management -> Build**: 21 rows (0.0004%).

Most of this is the Unmapped rescue (a previously-Unmapped rawAction resolved by a recognized
service tag), plus a small number of decisive-service overrides (e.g. a rawAction that verb-classified
to Data Management but carries an `issues`/`submittals`/`rfis`/`admin` service tag, so service wins).
The much larger ~8,107-row `docs`-serviceGroup-to-Admin-Actions population 21.1-RESEARCH.md measured
is an UMBRELLA service (docs/sheets/bridge) deferring to an already-correct, more granular verb
refinement — by design (locked decision) it produces **zero** module movement here, because the
verb taxonomy's Design Collaboration / Datum / Admin Actions splits are intentional, not bugs, and
an umbrella service never flattens them back to Data Management.

This is **not** a Model Coordination reclassification — that was already fixed 2026-06-05 by
commit `6164cfae`, which redirected all `issue-*` verbs to Build and excluded Model Coordination
from the donut entirely. `docs/activity-module-audit.md`'s "~966 Model Coordination" figure is stale
(untracked, predates that commit) and is superseded by this live evidence — it should not be
cited going forward.

The service-attributed/verb-inferred split above (99.98% / 0.0180%)
is the live figure the Overview tab's TRUTH-03 caveat should state (wired in plan 21.1-04), replacing the
stale "~40.7% disagreement" framing (that number was always `AccActivity`'s population rate, not
a disagreement rate).

## Owner-delegated mapping review (21.1-04 checkpoint)

At the plan 21.1-04 Task 3 checkpoint (live `:3100` preflight, 2026-07-06), the owner reviewed the
"Activity by module" panel, questioned two specific action groups (`publish-entity`,
`create-version-set`), and delegated the full module-attribution mapping review: *"I'll hand that
to you — review the types of activities and the modules assigned, use your best effort."* The
orchestrator audited all 122 live `(rawAction, service)` combinations and applied corrections 1-4.
At the final look the owner returned the verdict verbatim: **"approved BUT move sheets and friends
to the Build module"** — correction 5, owner-directed, which supersedes the Design Collaboration
destination in corrections 1-2.

All five corrections live in `lib/acc/activityClassification.ts` (`SERVICE_TO_MODULE`,
`MODULE_OVERRIDES`, `EXTRA_ACTIONS`). Row volumes are from live-DB queries against the same
per-`(project, action, service)` aggregate this script uses (4,722,412 total activities):

Deliberately NOT moved:

- `publish-entity` (51 rows) **stays Design Collaboration** (owner-confirmed): it is the
  docs-tagged Revit model publish — Design Collaboration's publish workflow — not a Sheets action.
  `send-entity-to-project` likewise stays Design Collaboration via the catalog.
- `restore-version` and `create-set` stay Data Management (Docs file-versioning/Sets features,
  not part of the Sheets cluster).
- `sheets` stays in `UMBRELLA_SERVICES`: it still never overrides an already-mapped verb result,
  it only rescues otherwise-Unmapped actions (now into Build).

**Net effect on the Overview donut:** 24,386 rows (0.52% of total activity — sheet verbs 24,232
plus the correction-1/2 rescue and version-set rows) land in Build instead of Design
Collaboration/Data Management. Per-module (AFTER, this run): Build 320,793;
Data Management 4,378,510; Admin Actions 23,024; Design Collaboration **53**; Datum 32;
Unmapped 0. The Design Collaboration slice shrinking to a ~53-row sliver (`publish-entity` +
`send-entity-to-project`) is honest and expected — the module's real activity in this account is
Revit-publish events only; the donut must not pad it. The service-attributed/verb-inferred caveat
split (99.98% / 0.0180%) is unchanged — these corrections change which module a row lands in, not
its `attributedBy`.
