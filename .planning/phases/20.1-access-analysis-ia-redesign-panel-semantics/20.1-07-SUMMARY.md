## Root Cause — Item 4 (GUID leak), with evidence

`app/(dashboard)/access-analysis/projectFilter.ts`'s `projectOptions()` builds the picker's option list from `[...roleRows, ...moduleRows, ...(timelineRows ?? []), ...(coordinationData?.rows ?? [])]`, keeping only the FIRST occurrence of each `projectId` (`if (!byId.has(r.projectId)) byId.set(...)`). `roleRows` is first, sourced from `lib/server/accessInstanceView.ts`'s `loadInstanceView()`.

Grepped every `db.$queryRaw`/`db.accDcProject.findMany` project-name-resolution site feeding these four arrays:

| Source (feeds picker array) | Before | After |
|---|---|---|
| `lib/server/accessInstanceView.ts` (`roleRows`, first priority) | `projectById.get(pu.projectId)?.name ?? pu.projectId` — only queried `AccDcProject`, fell back to the **raw GUID** | `resolveProjectName(buildProjectNameMap(liveProjects, dcProjects), pu.projectId)` — merges live `AccProject` + `AccDcProject`, falls back to `"Unknown project"` |
| `lib/server/moduleActivityView.ts` (`moduleRows`) | `nameById.get(projectId) ?? projectId` — same DC-only + raw-GUID-fallback bug | Same merged-map fix (preserves the pre-existing `"Account-level"` synthetic-project branch for empty `projectId`) |
| `lib/server/activityTimelineView.ts` (`timelineRows`) | Identical bug, identical fix | Same fix |
| `lib/server/coordinationByProjectView.ts` (`coordinationData.rows`) | Already correct (`buildProjectNameMap`/`resolveProjectName`) | Unchanged |
| `lib/server/permissionLevelView.ts` (feeds `PermissionLevelChart`, not the picker) | Already correct | Unchanged (used as the reference implementation for this fix) |

Because `roleRows` (from `accessInstanceView.ts`) is listed FIRST in `projectOptions()`'s union, its bug alone was enough to leak a bare GUID for any project synced live via the APS account-roles API (`AccProject`) but not yet captured by the Data-Connector snapshot crawl (`AccDcProject`) — exactly the "some projects" symptom the owner described. `moduleActivityView.ts`/`activityTimelineView.ts` carried the identical latent bug (would have leaked a GUID for a project unique to module/timeline activity with zero project-user memberships); fixed for the same reason even though `roleRows`'s fix alone likely closed the owner-visible symptom, since leaving a duplicate bug live in adjacent loaders feeding the SAME picker would be dishonest given the ask was "find every source."

New regression tests (`lib/server/accessInstanceView.test.ts`) pin: resolution from `AccProject` alone (previously DC-only), `AccProject` wins on conflict, `"Unknown project"` — never the raw GUID — when absent from BOTH sources, and pre-existing DC-only test fixtures (no `liveProjects` field) still resolve unchanged (backward-compatible optional field).
