**Researched:** 2026-07-03

**Confidence:** HIGH (all claims grounded in repo source reads + live read-only DB aggregate queries against the local PostgreSQL instance this pass)

## Summary

Phase 20.1 has no new external technology. Every one of the six owner UAT items is
solvable with modules and patterns that already exist in this repo: `components/ui/tabs.tsx`
(shadcn wrapper over the already-installed `radix-ui` package) for the tab shell, the
existing `EChart`/stacked-bar support for the two panel-semantic pivots, the existing
`AccDcProjectUserCompany`/`AccDcCompany` join already powering "Users by company" for the
new company graph, and the existing lazy-load-on-expand pattern (`TerrainReveal`,
`FolderActivityReveal`) for per-tab data loading. No new npm dependency is needed; no new
Prisma migration is *required* (though one is a legitimate, weighed option for the PERM-01
reframe — see Architecture Patterns §3).

The riskiest item is not a UI problem — it is `AccessAnalysisCharts.tsx`'s 722-line,
11-panel monolith turning into a **shared-state-plus-six-tab-panels** component. The tab
redesign is also the natural moment to fix the `mainCharts.tsx` `Promise.all` fan-out growth
that Phase 20's own STATE.md decision log already flagged for review ("once 3+ new loaders
share a domain"): this phase adds up to 3 new loaders on top of Phase 20's 11, which would
push the flat fan-out to 14 — past the ~12-entry PITFALLS.md warning threshold — unless the
non-Overview tabs' data is fetched lazily on first tab activation, reusing the exact
`"use server"` action + lazy-`useEffect`-fetch pattern already proven by
`TerrainReveal`/`FolderActivityReveal`.

Two of the six items (PERM-01 reframe, ENG-01 pivot) required live data verification to
choose a safe, bounded query shape; both came back well within the existing OOM-guard class
(tens of thousands of rows, not millions). One item (role-click scroll-jump) could not be
root-caused via static analysis — no `router.push`/`scrollIntoView`/`autoFocus` exists
anywhere in the access-analysis component tree — and needs a live-browser reproduction as
the plan's first task, not a blind fix.

**Primary recommendation:** Split `AccessAnalysisCharts.tsx` into a thin shell (shared
state: `selected`, `sliceFilters`, `profileEmail`, `peopleSheet`, the global `ProjectPicker`
+ `FilterBanner`, `StatStrip`, coverage header) that mounts a `<Tabs>` root, plus six new
per-tab panel components under `app/(dashboard)/access-analysis/components/` (flat,
matching the existing convention — no subfolder). Fetch Overview-tab data eagerly in
`mainCharts.tsx`; fetch every other tab's data lazily via a `"use server"` action on first
tab activation, mirroring `TerrainReveal`/`FolderActivityReveal` exactly.

## Architecture Patterns

### §1. Tab shell & per-tab data loading

**What:** Split `AccessAnalysisCharts.tsx` (currently 722 lines, 11 panels — read in full
this pass) into:
- A thin shell component (keep the name `AccessAnalysisCharts`) owning: `selected`
  (`Set<string>`, the global project-picker state), `sliceFilters`, `profileEmail`,
  `peopleSheet`, the `StatStrip`, the TRUTH-01 coverage header line, `ProjectPicker`, and the
  idle-tip/`FilterBanner` swap — all currently rendered ABOVE the panel grid (lines 281–332
  of the current file). These render **above** the `<Tabs>` root per CONTEXT.md's locked
  "Filter scope" decision (one global picker for every tab, Compare included).
- Six new flat sibling components under `app/(dashboard)/access-analysis/components/`
  (matching the existing flat convention — no subfolder anywhere in this directory today):
  `OverviewTabPanel.tsx`, `RolesTabPanel.tsx`, `UsersTabPanel.tsx`, `CompaniesTabPanel.tsx`,
  `ProjectsTabPanel.tsx`, `CompareTabPanel.tsx`. Each receives already-filtered/summarized
  props from the shell (the shell keeps ownership of `useMemo`'d summaries — `roleSummary`,
  `companySummary`, `activityByRoleSummary`, etc. — exactly as today; only the *rendering*
  moves into per-tab components).

**When to use:** This is the only way to keep `AccessAnalysisCharts.tsx` from crossing
~800–900 lines once the 3 new panels (ENG-01 pivot, PERM-01 reframe, company graph) are
added on top of the current 11, and it directly implements the locked "6 tabs" decision.

**Data-loading tie-in:** `mainCharts.tsx` (currently 106 lines, 11-entry flat `Promise.all`
— read in full this pass) should keep eager-loading only what the **Overview** tab and the
shell need on first paint: `loadInstanceView`, `loadModuleActivity`, `loadActivityTimeline`,
`loadIngestFreshness`, `loadProjectCoverage`, `loadDcCoverage`, `loadTerrainProjects` (for
the Compare tab's project-option list, not its data), and whatever the picker/KPI strip
needs account-wide. Every other tab's heavier loaders (`loadActivityByActor`,
`loadCoordinationByProject`, the new PERM-01/ENG-01/company loaders, `loadFolderActivityProjects`/`loadFolderActivityTree`, `loadTerrainForProject`/`loadOverviewTerrain`)
should fetch lazily on first tab activation via the **existing** `"use server"` action +
`useEffect` pattern already proven by `TerrainReveal`/`FolderActivityReveal` — i.e., a
`visitedTabs: Set<TabId>` (or per-tab `loaded` flag) in the shell, and each tab component
calls its `"use server"` loader action once when it's first activated, caching the result in
shell state so switching back doesn't re-fetch. This is the concrete mechanism that resolves
STATE.md's flagged "`mainCharts.tsx`'s `Promise.all` fan-out... should be reviewed for
consolidation once 3+ new loaders share a domain" — this phase adds 3 new loaders,
crossing that threshold, and the tab redesign is the natural point to convert growth from
"more eager parallel entries" into "lazy per-tab fetch," which also improves initial
`/access-analysis` load time (a page-load metric Phase 20's own success criteria already
spot-checked).

**Radix Tabs default-mount behavior:** `TabsPrimitive.Content` (from the `radix-ui` package,
`components/ui/tabs.tsx:78-89`) unmounts inactive tab panels from the DOM by default (no
`forceMount`). This is desirable here (it is what makes the lazy-fetch-on-activation pattern
correct — an inactive tab's DOM/data don't need to exist), but it means:
- Existing Vitest tests that currently assert on multiple sections simultaneously in one
  render (`AccessAnalysisCharts.test.tsx`, 428 lines / 33 test cases, read this pass) will
  need to `fireEvent.click`/`userEvent.click` the relevant `TabsTrigger` before querying
  content that now lives in a non-default tab. This is a real, non-trivial test-migration
  cost — budget a dedicated task for it, not a side effect of the panel-split tasks.

### §2. ENG-01 pivot — activity recency by role

**What:** Replace `lib/server/signInRecencyView.ts` (sign-in-based) with a new loader, e.g.
`lib/server/activityRecencyView.ts`, that:
1. Computes `MAX("createdAt")` per `(projectId, userEmail)` from `AccActivityAccds` alone
   (CONTEXT.md is explicit: "each user's latest `AccActivityAccds` event" — not the unified
   accds+DC-backfill union `loadActivityByActor` uses for volume).
2. Joins that per-membership "last activity" date onto the **same** DC-covered membership
   population the current dormant panel uses (`AccDcProjectUser`, joined via `AccDcUser` for
   name/company — mirrors `signInRecencyView.ts`'s existing `assembleSignInRecency` shape),
   but additionally attributes each membership's **role(s)** via `AccDcProjectUserRole` +
   the existing `mergeRoleNames` (`AccRole`-over-`AccDcRole`) resolution already used in
   `lib/server/accessInstanceView.ts:35-43` — reuse `mergeRoleNames`, do not re-derive it.
3. Buckets into the same 5 bands as `signInRecencyCounts.ts` (`<30d`/`30–90d`/`90–365d`/
   `>365d`/`Never active` — reuse the exact day-boundary logic in `bucketSignInRecency`,
   renamed conceptually, e.g. `bucketActivityRecency`), but summed **per role** (0 roles →
   `UNKNOWN_ROLE`, 1 role → that role, 2+ roles → `MULTIPLE_ROLES`, exactly mirroring
   `roleActivityCounts.ts`'s `summarizeActivityByRole` attribution rule) to produce a
   role×band stacked structure for the Roles-tab chart, AND keep the flat per-membership row
   list (with role, company, last-activity date) for the Users-tab drill/detail view
   (CONTEXT.md: "Users → dormancy/recency detail and drill lists (the user-level cut)").

**Live-verified sizing (read-only queries against the local Postgres DB, this research
pass):**
- `AccDcProjectUser` (bucketing population): **22,835** rows — same population/coverage
  class as the current (about-to-be-replaced) sign-in panel.
- Distinct `(projectId, userEmail)` pairs with `MAX(createdAt)` over ALL `AccActivityAccds`:
  **12,269** rows — small, bounded, same order of magnitude as `loadActivityByActor`'s
  existing ~2.7k-row unified query; a plain `GROUP BY` (no raw-row dump) is safe here.
- Of the 22,835 DC memberships, 21,908 (96%) belong to accds-covered projects; of those,
  only **7,276 (33.2%)** have at least one matching `AccActivityAccds` row by
  `(projectId, lower(email))`. **This means roughly two-thirds of memberships will land in
  "Never active"** — a real, expected distribution (verified, not degenerate: the *previous*
  sign-in pivot itself was built specifically to replace a 100%-null dead field with a real
  ~32%-active signal; this new distribution is the same order of magnitude, just inverted).
  Flag prominently in the plan: the panel's copy/caption must make clear that "Never active"
  means "no recorded activity in the ACCDS-crawled window," not "never used ACC," both
  because ACCDS retention is bounded (~12 months, per the existing TRUTH-02 `dataFloor`
  convention) and because accds itself only covers 956/1,153 projects.
- accds distinct `projectId` coverage: **956** — confirms the CONTEXT.md-cited "956/1,153"
  figure is currently accurate; still must be read live (`loadDcCoverage`-style pattern, or
  a small new count), never hardcoded.

**Anti-pattern to avoid:** Do not reuse `loadActivityByActor`'s unified accds+DC-backfill
query for this panel — CONTEXT.md explicitly scopes ENG-01's recency signal to
`AccActivityAccds` only, and mixing in DC-backfill `AccActivity` rows would silently change
which events count as "recent," breaking the coverage caption's accuracy.

### §3. PERM-01 reframe — permission volume by level

**What:** Add a new bounded aggregate reading `AccFolderPermission` (the raw ~6.04M-row
table) joined to `AccFolder` (for `projectId`) and `AccRole` (for role name), grouped by
`(projectId, roleId, permType)` — i.e. a **different query shape** than the per-project
`loadFolderPermRows` owned by `lib/server/folderPermQuery.ts`. Do **not** route this through
`folderPermQuery.ts` — that module's own header comment explicitly reserves it for "the
shared base join" consumed per-project by the two terrain loaders, and explicitly says "Do
NOT add single-use queries here." An account-wide `GROUP BY` aggregate for a bar chart is a
legitimately different consumer, exactly analogous to how `AccFolderPermissionSummary`'s
Ph18 backfill script already has its own separate `GROUP BY` SQL against the same raw table
rather than reusing `folderPermQuery.ts`.

**CRITICAL live-verified finding — `permType` vocabulary does NOT match `PermTier`:**
CONTEXT.md flagged this as a VERIFY item ("Permission-level vocabulary must map to the
ACC-aligned `permissionMapping` levels (committed 8162f72) — VERIFY exact level names"). A
live read-only query against `AccFolderPermission.permType` this pass returned exactly 6
distinct stored values:

| Stored `permType` (live, verified) | Row count |
|---|---|
| `View Only` | 5,917,818 |
| `View+Download` | 60,802 |
| `View+Download+Upload+Edit` | 48,761 |
| `View+Download+Upload` | 11,059 |
| `Full Controller` | 2,145 |
| `Upload Only` | 25 |

The `PermTier` type in `lib/acc/permissionMapping.ts:20-26` declares a **different** 6-value
set (`"View Only" | "View+Download" | "View+Download+Publish markups" |
"View+Download+Publish markups+Upload" | "View+Download+Publish markups+Upload+Edit" |
"Full administrative controls"`) — no "Publish markups" tier exists in the live data at
all, and the top/bottom labels differ verbatim (`Full Controller` vs. `Full administrative
controls`; `Upload Only` has no `PermTier` equivalent). **Do not run `mapActions()` against
stored rows or assume the two vocabularies are interchangeable** — `mapActions()` operates
on the raw `actions[]` array and is (per its own file header) called at *ingest* time in
`lib/acc/folderCrawl.ts`; the `permType` column already holds a finished, ingest-time label
that is a **different, older/narrower vocabulary** than the `PermTier` type currently
exports. **Recommendation: use the live stored `permType` strings verbatim as the chart's
6 stack segments** — do not attempt to remap through `permissionMapping.ts`. This is simpler
and more honest (it reflects what's actually in the DB) than reconciling two label sets that
have silently diverged.

**Row-count bound (live-verified, this pass):** the account-wide
`GROUP BY (AccFolder.projectId, AccFolderPermission.roleId, AccFolderPermission.permType)`
aggregate returns **60,110 distinct rows** — the same order of magnitude as
`AccFolderPermissionSummary`'s existing 22,082-row `(projectId, roleId)` materialization
(60,110 ≈ 22,082 × ~2.7 average tiers per role/project). This is safely within the existing
loader class (comparable to or smaller than `roleRows`/`view` already loaded for the whole
page) and does **not** require a materialized projection or a new migration. Recommend: a
new `lib/server/permissionLevelView.ts` loader with a 5-minute TTL cache (matching sibling
loaders' convention), returning rows shaped like the existing `PermissionFootprintRow` but
with `permType` + `folderCount` instead of `totalBytes` — feed it through a new
`summarizePermissionLevel` transform that mirrors `summarizePermissionFootprint`'s existing
top-10 + "Other" role bucketing (`app/(dashboard)/access-analysis/permissionFootprintCounts.ts:52-124`),
producing one **stacked** ECharts bar series per tier instead of one flat series.
`AccFolderPermission`'s existing `@@index([roleId])` (Phase 09, DB-01) makes this `GROUP BY`
index-friendly.

**Chart mechanics:** `EChart`'s `onEvents` click payload already types `seriesName` (see
`components/ui/EChart.tsx:23-26`) alongside `name` — a stacked-bar click handler can read
`(name, seriesName)` to know exactly which `(role, tier)` cell was clicked, enabling a
tier-scoped drill (not just a whole-role drill) if desired; the simpler, CONTEXT.md-matching
default is a whole-bar (role) drill identical to the current `PermissionFootprintChart`'s
`toggleDrill` pattern.

### §4. Compare tab — terrain relocation & picker removal

**What:** `FolderPermissionTerrain.tsx` (`app/(dashboard)/access-analysis/components/`, read
in full this pass) currently owns three internal, **self-managed** pieces of selection
state: `mode` (`"single" | "compare" | "overview"`, its own `ModeToggle`), `singleId`
(driven by its own `ProjectSelect` dropdown), and `selected: string[]` (driven by its own
`ProjectMultiSelect`, defaulting to `topStaffed.slice(0, 6)` — the 6 most-staffed projects).
CONTEXT.md's locked decision removes `ProjectSelect`/`ProjectMultiSelect` (the terrain's
"own search bar/picker") and requires project selection to come from the page's global
picker (`selected: Set<string>` in the shell) instead.

**Naming collision to flag in the plan:** the terrain component's own internal `Mode` type
already includes a value literally named `"compare"` (its floating-stacked-planes view). The
NEW page-level tab is *also* called "Compare." These are two different things (a page tab
vs. one of the terrain's three internal view modes) — the plan and any UI copy must keep
this distinction explicit to avoid confusing "the Compare tab" with "the terrain's Compare
mode" (which remains one of three toggle options *inside* that tab, per CONTEXT.md: "existing
terrain view modes... are preserved as-is").

**Recommended rewiring (does not touch geometry/camera/scene code — `terrainViewModel.ts`,
`useFolderPermissionTerrainCamera.ts`, `TerrainStage.tsx` all stay untouched, satisfying
"does not redesign the terrain itself"):**
1. Add a new prop to `FolderPermissionTerrain` (e.g. `externalSelectedIds?: string[]`) and a
   prop to suppress the internal pickers (a sibling to the existing `singleProject` prop,
   which already hides pickers for the *different* template-mty single-fixed-project case —
   do not reuse `singleProject` itself, its semantics are "there is exactly one project,
   period," not "selection comes from elsewhere").
2. Keep `ModeToggle` (single/compare/overview) — CONTEXT.md preserves all three view modes —
   but derive the *candidate project list* for whichever mode is active from
   `externalSelectedIds` instead of the component's own `useState`-managed `singleId`/
   `selected`, re-synced via a `useEffect` when `externalSelectedIds` changes.
3. Recommended mapping from the global picker's `selected` size to terrain mode/selection
   (an Open Question below — CONTEXT.md doesn't fully specify this, and the default page
   picker starts with **all** projects checked, per
   `AccessAnalysisCharts.tsx:147`: `useState<Set<string>>(() => new Set(options.map((o) => o.id)))`):
   - `selected.size === 0` → `mode="overview"` (loadOverview) — CONTEXT.md's explicit
     empty-state instruction.
   - `selected.size === 1` → `mode="single"`, `singleId` = that one project.
   - `selected.size >= 2` → `mode="compare"`, feed the intersection of the terrain's own
     existing `topStaffed` ranking with the global selection, capped at the terrain's
     existing default of 6 (reuses `topStaffed.slice(0, 6)` logic, just re-scoped to the
     global selection instead of the raw `projects` prop).
   - Since the global picker defaults to **all** projects selected, the Compare tab's first
     paint (with no user interaction) would hit the `>=2` branch — i.e., defaults into
     "compare" mode with the top-6-staffed projects, NOT `overview`. This is a reasonable
     interpretation of "empty state ... shows the existing all-folders overview" (that
     instruction most plausibly means "when the user has cleared/deselected everything," not
     "on first paint") but is exactly the kind of nuance to confirm with the owner or record
     explicitly as an assumption before building — see Open Questions.

### §5. Folder activity by company (new graph)

**What:** CONTEXT.md's literal ask is "each bar stacked by that company's top folders +
Other." Live-verified sizing (read-only queries, this pass) shows this needs a two-tier
design, not a single query:

| Query shape | Live row count |
|---|---|
| Raw `AccActivityAccds` rows with `folderId IS NOT NULL AND userEmail IS NOT NULL` | 4,108,152 |
| Distinct `(projectId, userEmail)` (folder-scoped) — safe headline-chart bound | **10,566** |
| Distinct `(projectId, userEmail, folderName)` (full cross-product CONTEXT.md's stacked-by-folder ask needs) | **190,049** |
| Distinct emails w/ folder activity → matched to `AccDcUser` (for company lookup) | 2,220 → 1,943 (87.5%) |
| Distinct `projectId` (folder-scoped) | 692 |
| `AccDcProjectUserCompany` rows vs. `AccDcProjectUser` rows (company-mapping coverage) | 18,329 / 22,835 (**80.3%**) |

**Recommendation (uses CONTEXT.md's own pre-authorized fallback: "if company×folder
stacking is too sparse, collapse to top-N companies with folder drill"):** the 190,049-row
full cross-product is an order of magnitude larger than every other loader on this page and
should **not** be computed account-wide on every load. Build this as a **two-pass** loader:
1. **Headline (eager within the Companies tab's lazy-load, bounded, cheap):** a new
   `lib/server/folderActivityByCompanyView.ts` that runs the SAME `(projectId, userEmail)`
   `GROUP BY` shape `loadActivityByActor` already uses, but filtered to
   `folderId IS NOT NULL` — 10,566 rows, safely small — then joins company via the exact
   same `(projectId, email)` → company Map-join pattern `summarizeActivityByCompany`
   (`app/(dashboard)/access-analysis/companyActivityCounts.ts:56-96`) already implements.
   Rank top-10 companies by summed folder-scoped activity; users with no company mapping
   fall into `UNKNOWN_COMPANY` (`app/(dashboard)/access-analysis/companyCounts.ts` — reuse
   the existing constant, do not invent a new label), which the 80.3%-coverage figure above
   confirms will be a real, non-trivial bucket (~20% of memberships) that must render, not
   hide.
2. **Drill (lazy, on click):** a small `"use server"` action, scoped to the clicked
   company's member emails only, that queries `AccActivityAccds` folder breakdown for just
   those emails — bounded by construction (one company's users, not the whole account) —
   mirroring `loadFolderActivityTree`'s existing per-project lazy-drill shape
   (`lib/server/folderActivityView.ts:115-134`) but keyed by company instead of project.

This avoids ever materializing the 190,049-row cross product while still delivering the
"which folders is this company touching" story on click, and stays inside the existing
"aggregates server-side SQL/`groupBy` only, never `findMany` + JS reduce" convention at both
steps.

### §6. Role-click scroll-jump bug (UAT item 5)

**What was ruled out by static analysis (grepped across the entire `access-analysis`
component tree, this pass):** no `router.push`/`router.replace`/`useRouter`/
`useSearchParams`/`history.pushState` exists anywhere in `app/(dashboard)/access-analysis/`.
No `scrollIntoView`/`window.scrollTo`/`autoFocus` exists in the page's own components
(the one `scrollIntoView`-adjacent hit repo-wide, `TerrainControls.tsx`, is the terrain's
own dropdown-outside-click handler — unrelated to a page-level scroll jump and not on the
click path from `RolesPieChart`).

**Most plausible mechanism (needs live-browser confirmation, not further static analysis):**
clicking a role in `RolesPieChart`'s legend (`toggleDrill`, `RolesPieChart.tsx:117-122`)
calls `onSliceClick`, which the shell wires to `toggleSliceFilter("role", val)`
(`AccessAnalysisCharts.tsx:158-163`). This flips `sliceFilters`, which:
1. Swaps the idle-tip `<p>` for `<FilterBanner>` right below the `ProjectPicker`
   (`AccessAnalysisCharts.tsx:319-332`) — a DOM structure change near the top of the page.
2. Simultaneously recomputes `roleSummary` via `applySliceFilters(...)`
   (`AccessAnalysisCharts.tsx:194-197`) — which can shrink `RolesPieChart`'s own legend list
   substantially (from every role down to only the roles co-held by members who hold the
   clicked role), changing that panel's own height at the same instant, in the very panel
   the user just clicked inside.
3. Every panel on the page is wrapped in `<Reveal>` (`components/ui/animated-list.tsx:55-63`),
   which uses framer-motion's `whileInView`/`viewport={{ once: true, margin: "-40px" }}` —
   IntersectionObserver-driven. This is stubbed to a no-op in the Vitest environment
   (`vitest.setup.ts`, confirmed via `.planning/codebase/TESTING.md`), which is exactly why
   this class of bug would never surface in the unit-test suite and must be reproduced in a
   real browser.

**Recommendation:** make live browser reproduction (Chrome DevTools Performance/Layout-Shift
recording while clicking a role slice) the plan's **first task** for this item, before any
code change. Cheap, non-destructive first things to try once reproduced: (a) keep the idle
tip and `FilterBanner` both permanently mounted, toggling visibility via CSS instead of a
JSX ternary (removes the mount/unmount at the top of the page as a variable); (b) check
whether the jump disappears if `RolesPieChart`'s own legend list is given a `min-height` so
its collapse doesn't change panel height. Do not guess a fix without reproducing first —
CONTEXT.md itself frames this as "diagnose and fix," not "apply a known fix."

## Common Pitfalls

### Pitfall 1: Treating `permType` and `PermTier` as the same vocabulary
**What goes wrong:** Building the PERM-01 reframe against `lib/acc/permissionMapping.ts`'s
`PermTier` labels (e.g., expecting a "Publish markups" tier) when the live `AccFolderPermission.permType`
column has a different, narrower 6-value set with no such tier.
**Why it happens:** Both are called "permission tier/level" in code comments and CONTEXT.md;
`mapActions()` looks like the obvious source of truth but is an ingest-time function over a
different input (`actions[]`), not a live transform of the stored `permType` string.
**How to avoid:** Use the stored `permType` strings verbatim (see Architecture §3 table) as
the chart's segment labels. Do not call `mapActions()` against DB rows.
**Warning signs:** A stacked-bar legend with 6 entries that don't match any list in
`permissionMapping.ts`, or a segment count that doesn't match the live 6 values above.

### Pitfall 2 (repo-wide convention, reconfirmed this phase): `AccFolderPermissionSummary.totalBytes` / any new BigInt column is `BigInt`
**What goes wrong:** A new PERM-01 loader crosses the RSC→client boundary with a raw
`BigInt` value (`folderCount`/`_count` results are plain numbers in Postgres `COUNT(*)`, but
double-check any column pulled directly off `AccFolderPermission`/`AccFolderPermissionSummary`).
**How to avoid:** Convert at the server-loader boundary only, same as `permissionFootprintView.ts:50`
already does (`Number(r.totalBytes)`).

### Pitfall 3: Account-wide cross-product queries silently ballooning row count
**What goes wrong:** The company×folder graph's literal CONTEXT.md ask, if implemented as
one flat `GROUP BY (projectId, userEmail, folderName)` query account-wide, returns 190,049
rows — safe from an OOM standpoint (it's a `GROUP BY`, not a raw-row dump) but large enough
to be a real page-load cost and a maintenance/test-fixture burden disproportionate to a
top-10-companies chart.
**How to avoid:** Two-pass design (§5) — small headline aggregate eagerly, folder-level
detail only for the clicked company, lazily.
**Warning signs:** A "bounded output" Vitest test (Ph21-convention, per CONTEXT.md
Verification Expectations) that has to assert a ceiling in the hundred-thousands instead of
the thousands — that's the signal the query needs re-scoping, not a bigger assertion.

### Pitfall 4 (repo-wide, PITFALLS.md #4, reconfirmed): `mainCharts.tsx`'s `Promise.all` fan-out
**What goes wrong:** Phase 20 left the fan-out at 11 entries, "comfortably under" the ~12
warning threshold. Phase 20.1 naively adding 3 more flat entries (ENG-01 pivot loader,
PERM-01 reframe loader, company-graph loader) reaches 14 — over threshold — while also now
fetching data for tabs the user may never open.
**How to avoid:** Convert non-Overview-tab loaders to lazy-on-first-activation (§1) instead
of adding them to the eager fan-out. This is a direct, better resolution of the exact
concern the Phase 20 STATE.md decision log already flagged for review.

### Pitfall 5: URL/router-driven tab state reintroducing the scroll-jump class of bug
**What goes wrong:** If a URL-param-backed tab implementation is chosen (an
Alternatives-Considered option, not the default recommendation) via `router.replace`, Next.js's
default navigation behavior scrolls to top unless `{ scroll: false }` is passed — this would
be a **second**, easier-to-trigger source of unwanted scroll jumps stacked on top of the
existing UAT-5 bug, and would need to be fixed in the exact same class of investigation.
**How to avoid:** Prefer plain client `useState` for tab selection (the recommended default,
Standard Stack "Alternatives Considered"); if URL-synced tabs are chosen anyway, any
`router.replace`/`push` call must pass `{ scroll: false }`.

### Pitfall 6: Radix `Tabs.Content` unmounting breaks existing test assumptions
**What goes wrong:** `AccessAnalysisCharts.test.tsx` (428 lines, 33 tests) currently queries
multiple sections in one render. Post-redesign, non-default-tab content won't be in the DOM
until its `TabsTrigger` is clicked; tests that don't account for this will fail with
"element not found," not because the feature is broken.
**How to avoid:** Budget an explicit test-migration task; each test asserting on non-Overview
content needs a `userEvent.click(screen.getByRole("tab", { name: ... }))` first.

-- Source: pattern verified against lib/server/folderPermQuery.ts's existing per-project

## Open Questions

1. **What does the Compare tab show on first paint, given the global picker defaults to ALL projects selected?**
   - What we know: CONTEXT.md locks "Empty state: Compare tab with no project selected shows
     the existing all-folders overview." The global picker's actual default state
     (`AccessAnalysisCharts.tsx:147`) is **all** projects checked, not zero.
   - What's unclear: whether "no project selected" means (a) the picker's `selected` Set is
     literally empty (a state the user must actively create by unchecking everything), or
     (b) CONTEXT.md's author was implicitly assuming a Compare-tab-scoped selection that
     starts empty independent of the global picker.
   - Recommendation: default to interpretation (a) — reuse the one global `selected` Set
     everywhere, exactly as CONTEXT.md's locked "Filter scope" decision requires ("every tab
     including Compare reads the same selection") — and accept that first paint on Compare
     will show `mode="compare"` with the top-6-staffed intersection (§4), not the overview.
     Flag this interpretation explicitly to the owner at plan-check time since it's a
     visible first-paint behavior choice, not a pure implementation detail.

2. **Exact root cause of the role-click scroll-jump bug.**
   - What we know: no router/scrollIntoView/autoFocus mechanism exists in the component
     tree (§6); the bug is real per direct owner feedback.
   - What's unclear: whether it's scroll-anchoring interacting with `RolesPieChart`'s own
     legend-height collapse, the `FilterBanner` mount, both, or something else entirely
     (e.g., an ECharts `resize()` side effect inside `echarts-for-react` on option change).
   - Recommendation: live-browser reproduction as the plan's literal first task (§6) — do not
     schedule a fix task before a repro task.

3. **Whether the PERM-01 reframe's live query should get a 5-min TTL cache or stay uncached.**
   - What we know: sibling loaders (`permissionFootprintView.ts`, `signInRecencyView.ts`)
     use a 5-minute in-process TTL cache; `ingestFreshnessView.ts` deliberately has none
     because CONTEXT.md required a static, non-stale-cacheable read for that specific panel.
   - What's unclear: nothing product-relevant — this data changes once per ingest cycle
     (daily), so a 5-min cache is safe and consistent with the majority sibling pattern.
   - Recommendation: use the standard 5-minute TTL cache (matches `permissionFootprintView.ts`/
     `signInRecencyView.ts`, not the `ingestFreshnessView.ts` exception).
