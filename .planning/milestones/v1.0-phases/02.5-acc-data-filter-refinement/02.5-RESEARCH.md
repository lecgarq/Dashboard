## User Constraints (from CONTEXT.md)

### Locked Decisions

**Hide behavior & cascading**
- Edges to/from hidden user nodes are **fully hidden** (not dimmed). Matches spec wording.
- **Cascade hide is recursive**: when a Project/Role/Module node has zero visible connected users it auto-hides; if hiding a Project then orphans a Role with no other projects, the Role also hides; etc. Graph only shows what's relevant to the current filter.
- After filters change the visible node set, the **physics simulation reflows the layout** (visible nodes settle into a new arrangement based on remaining edges). This will re-trigger Phase 3's "Stable" badge once it settles.
- **Empty state**: when zero nodes match, show an overlay message ("No users match these filters — adjust filters to see results") with a "Clear filters" button.
- **Click-through on hidden node positions**: nothing happens. No hit-testing on hidden nodes.
- Filters **persist in URL query params** (e.g. `?modules=x,y&from=...&to=...`). Shareable, survives refresh, follows the existing nav-state pattern from Phase 1.
- **Drag-while-filter-changes**: defer the hide until the drag interaction ends, then apply.
- **Hide transition**: brief fade-out (~150ms). Animation is acceptable; keep it cheap on Cosmos.gl and Canvas2D.
- **Filter panel header** shows a count summary like `Showing 47 of 312 users` whenever any filter is active.
- **"Clear all filters" button** is visible in the filter panel only when at least one filter is non-default; one click resets everything to all-on / empty range.

**companyRole extraction & display**
- Source: **ACC Admin API user record top-level field**. Extract during the existing ACC sync into the user table.
- **Null/missing values**: persist null in DB; display as `Unspecified` in the side panel and as an `Unspecified` bucket in the filter dropdown.
- **Filter UX**: multi-select dropdown of distinct values **with a search box at the top** for long lists.
- **Side-panel display**: plain row alongside other user fields (e.g. `Company Role: Architect`), consistent with existing panel layout. No special badge.

**Date filter semantics**
- The "relevant date" field is **`lastActivity` / `lastSignIn`** on the user. (Use case: stale-user / recent-activity analysis.)
- **Users with no `lastActivity` value are excluded** when a date range is active. With no range set, they're visible.
- **Default state on load**: no range set (both inputs empty) → all users visible. User opts in to filtering.
- **Input style**: two native `<input type="date">` fields labeled `From` and `To`. No date-picker dependency.
- Range is **inclusive** on both ends (matches spec).

**Module toggle logic**
- **Multi-module behavior**: a user with access to Modules A and B remains visible when A is toggled off and B is on. The user is filtered out only if **all** modules they have access to are toggled off (i.e. their access intersects only off modules). Matches spec wording literally.
- **Default state**: all module toggles ON → every user visible. User opts out per module to narrow down.
- **Toggle UI**: iOS-style switch toggles (one per module, vertical list).
- **Users with no module access**: always visible regardless of module toggles. Other filters (date, companyRole) still apply to them.

## Summary

Phase 2.5 has four implementation streams that touch different layers of the stack: (1) ACC API field extraction + DB storage for `companyRole` and `lastSignIn`, (2) `GraphFilters` type + `nodeMatchesFilters()` logic overhaul to support the new filter semantics, (3) filter UI overhaul in the controls panel (date inputs, module toggles, companyRole multi-select, URL persistence, empty-state, count header), and (4) graph renderer hide changes to make excluded nodes fully invisible (not dimmed) in both Canvas2D and Cosmos.gl.

The good news: the foundational hide infrastructure already exists. `rebuildVisibleIndices()` computes `visibleNodeIdxRef` and passes it to both the worker and the renderers. Canvas2D's `draw()` already only renders nodes whose index is in `userIndices` (the supplied visible subset). Cosmos.gl already receives `visibleIndices` in its init message. What is missing is: (a) the new filter fields on `GraphFilters`, (b) the module logic inversion, (c) the Cosmos.gl zero-size hide for excluded points, (d) the fade-out animation, (e) the URL query-param persistence, and (f) the ACC data extraction for the two new fields.

The `companyRole` field is available in the HQ v1 user record as `company_role` (confirmed by Autodesk ACC API naming conventions). The `lastSignIn`/`lastActivity` field is likely `last_sign_in` or `last_activity` in the raw API response — the current code already maps `created_at` → `addedOn`; the same pattern applies. Both fields flow through `AccMemberCache.data` (the `Json` blob in Prisma), so no schema migration is required if stored in the blob. However, extracting them for filtering requires surfacing them on the `AccGraphInstanceNode` and through the `SimNode`.

**Primary recommendation:** Store `companyRole` and `lastSignIn` in the existing `AccMemberCache.data` JSON blob (no new DB columns needed); surface them through `AccGraphInstanceNode` and `SimNode`; extend `GraphFilters` with the three new filter dimensions; implement URL-param persistence using Next.js `useSearchParams` + `useRouter`; make excluded nodes fully invisible via `setPointSizes(0)` in Cosmos and simply omit from `userIndices` in Canvas2D (which already works).

### Pattern 2: Extending GraphFilters for the New Semantics

**What:** The existing `GraphFilters` interface and `nodeMatchesFilters()` function in `AccUsersGraph.tsx` need three extensions: `companyRoles` multi-select, `dateFrom`/`dateTo` range, and module logic inversion.

**When to use:** Any time a new filter dimension is added.

```typescript
// Current interface (AccUsersGraph.tsx line 69)
interface GraphFilters {
  roles: string[];
  lastAddedBuckets: string[];
  adminAccess: "all" | "admin" | "non-admin";
  modules: string[];
}

// Extended interface
interface GraphFilters {
  roles: string[];
  lastAddedBuckets: string[];
  adminAccess: "all" | "admin" | "non-admin";
  // Module toggles: string[] of ENABLED modules (empty = all enabled conceptually)
  // Phase 2.5 replaces this with an explicit OFF set:
  disabledModules: string[];    // modules that are toggled OFF
  companyRoles: string[];       // selected company roles (empty = all)
  dateFrom: string;             // YYYY-MM-DD or ""
  dateTo: string;               // YYYY-MM-DD or ""
}

const DEFAULT_FILTERS: GraphFilters = {
  roles: [],
  lastAddedBuckets: [],
  adminAccess: "all",
  disabledModules: [],
  companyRoles: [],
  dateFrom: "",
  dateTo: "",
};
```

**Module filter logic (new semantics — inversion of current):**
```typescript
// Current (wrong for phase 2.5): shows only nodes that have ≥1 module in the filter list
// New: shows nodes unless ALL their modules are disabled
function nodeMatchesFilters(node: SimNode, filters: GraphFilters): boolean {
  // ... existing role/bucket/adminAccess checks ...

  // Module toggle: exclude only if ALL user's modules are toggled off.
  // Users with no modules always pass (they don't intersect any off-module).
  if (filters.disabledModules.length > 0 && node.modules.length > 0) {
    const allModulesOff = node.modules.every((m) => filters.disabledModules.includes(m));
    if (allModulesOff) return false;
  }

  // companyRole multi-select: empty = all visible; non-empty = must match
  if (filters.companyRoles.length > 0) {
    const role = node.companyRole ?? null;
    const bucket = role ?? "Unspecified";
    if (!filters.companyRoles.includes(bucket)) return false;
  }

  // Date range: only applies when at least one bound is set
  if (filters.dateFrom || filters.dateTo) {
    if (!node.lastSignIn) return false; // exclude users with no date when range active
    const nodeDate = node.lastSignIn.slice(0, 10); // YYYY-MM-DD
    if (filters.dateFrom && nodeDate < filters.dateFrom) return false;
    if (filters.dateTo && nodeDate > filters.dateTo) return false;
  }

  return true;
}
```

### Pattern 3: URL Query Param Persistence (Next.js)

**What:** Filters persist in URL using `useSearchParams` (read) + `router.replace` (write). This is the "existing nav-state pattern" referenced in CONTEXT.md — Phase 1 used `localStorage` for pan/zoom; Phase 2.5 uses URL params for filters (shareable, survives refresh).

**When to use:** Whenever filter state must survive navigation and be shareable.

```typescript
// Read on mount
const searchParams = useSearchParams();
const router = useRouter();
const pathname = usePathname();

function readFiltersFromUrl(params: ReadonlyURLSearchParams): GraphFilters {
  return {
    ...DEFAULT_FILTERS,
    companyRoles: params.get("roles")?.split(",").filter(Boolean) ?? [],
    disabledModules: params.get("moff")?.split(",").filter(Boolean) ?? [],
    dateFrom: params.get("from") ?? "",
    dateTo: params.get("to") ?? "",
    adminAccess: (params.get("admin") as GraphFilters["adminAccess"]) ?? "all",
  };
}

// Write on filter change (debounced ~300ms so typing in date inputs doesn't spam)
function writeFiltersToUrl(filters: GraphFilters) {
  const params = new URLSearchParams();
  if (filters.companyRoles.length)    params.set("roles", filters.companyRoles.join(","));
  if (filters.disabledModules.length) params.set("moff",  filters.disabledModules.join(","));
  if (filters.dateFrom)               params.set("from",  filters.dateFrom);
  if (filters.dateTo)                 params.set("to",    filters.dateTo);
  if (filters.adminAccess !== "all")  params.set("admin", filters.adminAccess);
  const qs = params.toString();
  router.replace(`${pathname}${qs ? `?${qs}` : ""}`, { scroll: false });
}
```

**Note:** `useSearchParams` requires wrapping the component in a `<Suspense>` boundary in Next.js app router. The `AccUsersGraph` is already a client component; check if its parent page already wraps in Suspense, or add one.

### Pattern 4: Cosmos.gl Full Hide via Zero Point Size

**What:** Cosmos.gl does not have a native "remove node" API — you hide a node by setting its rendered size to 0. This is the renderer-specific hide implementation for Cosmos.

**When to use:** Any time a filter change needs to hide nodes in the Cosmos GPU renderer.

```typescript
// In CosmosGraphRenderer.draw() or a new setVisibleIndices() method:
function buildNodeSizeBufferWithVisibility(
  nodeCount: number,
  connections: Int32Array | null,
  visibleSet: ReadonlySet<number>
): Float32Array {
  const sizes = new Float32Array(nodeCount);
  for (let i = 0; i < nodeCount; i++) {
    if (!visibleSet.has(i)) {
      sizes[i] = 0; // fully hidden — no pixel, no hit-test
      continue;
    }
    const degree = connections?.[i] ?? 0;
    sizes[i] = degree > 3 ? 6 : degree > 0 ? 4 : 3;
  }
  return sizes;
}
// Then: this.graph.setPointSizes(buildNodeSizeBufferWithVisibility(...));
```

**Canvas2D:** Already fully hidden — `CanvasGraphRenderer.draw()` iterates only `frame.userIndices` (the visible index subset). Excluded nodes are never drawn. No change needed to Canvas2D draw loop.

### Pattern 5: Fade-Out Animation (150ms, cheap)

**What:** The CONTEXT.md specifies a ~150ms fade-out when nodes hide. The constraint is "keep it cheap on Cosmos.gl and Canvas2D." The simplest approach: animate `opacity` on a React state transition or use a CSS transition on the canvas element alpha — NOT a per-frame GPU animation.

**Recommended approach:** A single CSS `transition: opacity 150ms ease-out` on a wrapper div that covers the graph canvas, triggered by a React state flag `isFilterTransitioning`. Set it true on filter change, false after 150ms. This avoids any WebGL shader changes and is zero-cost once the transition completes.

**Alternative (simpler):** Skip the animation entirely if it proves complex. The CONTEXT.md says "Animation is acceptable; keep it cheap." The planner may choose to defer animation to a polish task.

### Anti-Patterns to Avoid

- **Greying-out hidden nodes:** The CONTEXT.md hard-bans this. Do not set alpha to 0.1 or use `DIMMED_USER_COLOR` for filtered nodes. Zero size in Cosmos, skip in Canvas2D.
- **Client-side only filter storage:** Previous filter state uses `localStorage` (line 352 in AccUsersGraph.tsx). Phase 2.5 replaces this with URL params. Remove the `localStorage` read/write for `acc-graph-filters` — URL params are the new source of truth.
- **DB migration for companyRole:** Do not add a new Prisma model column for companyRole. Store it in the existing `AccMemberCache.data` JSON blob. The graph snapshot pipeline (`graphSnapshot.ts`) reads the JSON — just add extraction there.
- **Date picker library:** CONTEXT.md explicitly calls for native `<input type="date">`. No new dependency.
- **Module filter as "show only selected":** The current `filters.modules` logic is "include-list" semantics. Phase 2.5 requires "exclude-list" (disabled) semantics. The `disabledModules` rename makes this explicit and prevents logic confusion.

## Common Pitfalls

### Pitfall 1: ACC API Field Name Uncertainty for `companyRole`

**What goes wrong:** The HQ v1 users endpoint returns `company_role` (snake_case) in the raw JSON, but the codebase normalizes to camelCase. The existing extraction in `fetchAllAccUsers` already aliases `company_name || company` for the `company` field. If the field name isn't aliased correctly, it silently returns `undefined` for all users.

**Why it happens:** Autodesk's API mixes snake_case and camelCase across versions. The code already handles this with the `getString(u.company_name || u.company)` pattern.

**How to avoid:** Follow the same alias pattern:
```typescript
companyRole: getString(u.company_role || u.companyRole) || undefined,
```
Also: after the first sync post-implementation, log a sample of 3-5 raw API response fields (console.info in the sync mutation) to confirm the actual field name before removing the log.

**Warning signs:** `companyRole` is `undefined` for all users after sync. Add a temporary diagnostic log in `bulkAccSync` to print 2-3 user records' raw fields.

---

### Pitfall 2: `lastSignIn` Field May Not Exist on HQ v1

**What goes wrong:** The HQ v1 `/accounts/{id}/users` endpoint may not return a `lastSignIn` or `lastActivity` field. The current codebase captures `created_at` as `addedOn`. If `last_sign_in` doesn't exist in the response, all users will have `null` lastSignIn, which means the date filter will exclude all users when active.

**Why it happens:** Autodesk's HQ v1 API was originally designed for account management, not audit logging. Activity dates may be in a separate audit API or Data Connector.

**How to avoid:** 
1. In the `bulkAccSync` mutation, log a sample raw user record (one line, one user) to see all available fields.
2. If `last_sign_in` doesn't exist: fall back to `addedOn` (the `created_at`/`addedOn` field already captured). `addedOn` represents the date the user was added to the hub — not last activity, but a useful date proxy.
3. Document the fallback in code comments and in the plan's completion summary.
4. The planner MUST include a Wave 0 or Wave 1 task to verify the field name against the live API.

**Warning signs:** All `lastSignIn` values are `undefined` after sync. The date filter excludes everything when a range is set.

---

### Pitfall 3: Module Filter Logic Inversion Breaking Existing `filterOptions`

**What goes wrong:** The existing filter options builder computes `filterOptions.modules` as "modules that appear in at least one user" — used to populate the filter UI. Phase 2.5 changes modules from an include-list to an exclude-list. If the option builder and the filter logic are updated inconsistently, some module combinations will hide/show incorrectly.

**Why it happens:** The old `filters.modules` was "show only users with these modules selected." The new `disabledModules` is "hide users whose ALL modules are in this set." The UI must show ALL modules as initially ON and let users toggle off.

**How to avoid:** Rename the field from `modules` to `disabledModules` in `GraphFilters`. This makes the inversion explicit and causes TypeScript type errors at all existing callsites, surfacing the migration points.

---

### Pitfall 4: URL Persistence Requires Suspense Boundary

**What goes wrong:** `useSearchParams()` in Next.js app router requires the calling component to be wrapped in a `<Suspense>` boundary, otherwise it throws at build time with a "missing Suspense boundary" error.

**Why it happens:** Next.js app router streams components; `useSearchParams()` opts into dynamic rendering.

**How to avoid:** Wrap the `AccUsersGraph` component (or its parent in `page.tsx`) in `<Suspense>`. Check whether `page.tsx` in `(dashboard)/users/` already provides a Suspense wrapper.

---

### Pitfall 5: Cosmos.gl Zero-Size Points Still Participate in Physics

**What goes wrong:** Setting a point size to 0 via `setPointSizes()` hides it visually but does NOT remove it from the physics simulation. Hidden nodes continue to exert repulsion forces, which can cause visible nodes to cluster oddly.

**Why it happens:** Cosmos.gl separates rendering from simulation. `setPointSizes` is a rendering call.

**How to avoid:** The existing `postVisibilityToWorker()` already sends `visibleIndices` to the organic layout worker, which skips hidden nodes in physics. In Cosmos GPU-physics mode, `setConfigPartial` can reduce simulation for hidden nodes but there is no per-node physics toggle in Cosmos v3 beta. Accept that hidden nodes still influence Cosmos physics — the CONTEXT.md says "physics simulation reflows" on filter change, implying this is expected/acceptable behavior. If it produces obviously bad layouts, reduce `simulationRepulsion` slightly when filter is active. This is Claude's discretion territory.

---

### Pitfall 6: Drag-While-Filter-Changes Race Condition

**What goes wrong:** User is dragging a node when filters change. If `rebuildVisibleIndices()` runs mid-drag and hides the dragged node, the drag state references a stale node index, causing the renderer to track a ghost position.

**Why it happens:** Filter state updates are synchronous React state changes that immediately trigger `rebuildVisibleIndices()`.

**How to avoid:** Per CONTEXT.md decision: "defer the hide until the drag interaction ends, then apply." Implementation: check `isDraggingNodeRef.current` in the `useEffect` that calls `rebuildVisibleIndices()` on filter change — if dragging, store the new filters in a pending ref and apply after `pointerup`.

## Open Questions

1. **Exact field name for `companyRole` in HQ v1 response**
   - What we know: HQ v1 returns `company`, `role`, `status`. The `companyRole` field that Autodesk documented as the "role within the company" has been observed as `company_role` in BIM360 API responses.
   - What's unclear: Whether HQ v1 (not ACC Admin v1) exposes this field at all, or whether it is only available via ACC Admin v1 user detail endpoint.
   - Recommendation: Wave 0 diagnostic — add a temporary `console.info("[ACC raw user fields]", Object.keys(rawUser))` log in `fetchAllAccUsers` during the first sync after implementation. If `company_role` is absent, fall back to empty string (display as `Unspecified`).

2. **Exact field name for `lastSignIn`/`lastActivity` in HQ v1 response**
   - What we know: `created_at` is captured as `addedOn` (already working). The ACC Data Connector API provides richer audit fields but is a separate API entirely.
   - What's unclear: Whether the HQ v1 `/accounts/{id}/users` response includes any last-activity timestamp. Search results suggest the Data Connector API is the canonical source for this, but it requires a separate integration.
   - Recommendation: Same Wave 0 diagnostic as above. If the field doesn't exist, use `addedOn` as the date filter field and update the UI label to "Added On" rather than "Last Active." Document this as a known limitation.

3. **Suspense boundary for `useSearchParams`**
   - What we know: Next.js app router requires Suspense wrapping for `useSearchParams`.
   - What's unclear: Whether the existing `(dashboard)/users/page.tsx` already wraps `AccUsersGraph` in Suspense.
   - Recommendation: Check `page.tsx` in Wave 0 setup; add Suspense if not present.
