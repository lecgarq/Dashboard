## 1. VRAM & Hardware Constraints

| Debt Item | Risk | Mitigation |
| :--- | :--- | :--- |
| **Monolithic GPU Memory** | **CRITICAL** (OOM) | Implement a "Stage Unloader" that explicitly frees VRAM between Captioning and Segmentation. |
| **Device Contention** | **HIGH** | The Dashboard's `lod-query-encoder` and the `lod-training-pipeline` will compete for the same GPU. Needs a lock or queue. |
| **Model Weight Load Time** | **MEDIUM** | BLIP-2 and GDINO weights are ~12GB combined. Loading them on-demand per request will cause 30s+ initialization delays. |

## 2. API & Orchestration Debt

- **HTTP Timeouts**: tRPC / Next.js server actions have a standard timeout of 30-60s. The pipeline takes **20s per image**, meaning a 10-image batch will 100% time out without an async job worker.
- **File System Dependency**: The external pipeline relies on a `00_data` directory structure. Migrating this to a cloud-native or database-backed blob storage (e.g., Supabase Buckets or UploadThing) is required for scalability.
- **Python-Node Bridge**: Relying on subprocess calls or simple HTTP for a 40-minute job is fragile. Recommending a persistent WebSocket or event-bus (SSE) for progress reports.

## 3. Data Integrity & RAG

- **Vector Versioning**: If a user re-trains an image, we need to ensure the old embedding in `LodEmbedding` is invalidated to prevent "Hallucinations" in the graph.
- **Manual Finalization**: Currently, the pipeline saves a `batch.json` which must be manually "Uploaded" via the `lod:migrate` script. This should be automated into a post-processing hook in the Dashboard.

## 4. Components

- **Mask Quality**: Automatically choosing between RMBG-1.4 and SAM/GDINO can lead to "Edge Fraying" on complex Revit families (e.g., fine-mesh trusses). A human-in-the-loop "Approval" step is missing.
