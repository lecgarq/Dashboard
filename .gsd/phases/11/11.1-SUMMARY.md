# Summary: Redis Vector Cache Abstraction

## What was built

Migrated the `LodSearchCache` from PostgreSQL to Upstash Redis using the `@upstash/redis` HTTP client. The cache layer in `server/routers/lod.ts` was rewritten to use Redis hashes keyed by `lod:search:{queryHash}`. TTL-based expiry (24h) replaces the previous manual DELETE sweep on every search request.

Two additional references to `ctx.db.lodSearchCache` were cleaned up:
- `deleteFamily`: removed the stale-cache invalidation (stale result IDs are filtered out at read time; TTL handles cleanup).
- `uploadBatch` (admin): replaced `deleteMany()` with a Redis `SCAN` plus `DEL` loop to flush all `lod:search:*` keys after a full re-upload.

## Files modified

- `lib/redis.ts` (created) - Upstash Redis client singleton
- `server/routers/lod.ts` - cache read/write replaced with Redis; `SEARCH_CACHE_TTL_S` constant added; `CacheEntry` type defined
- `prisma/schema.prisma` - `model LodSearchCache { ... }` block removed
- `prisma/migrations/20260416220000_drop_lod_cache/migration.sql` - drops the `LodSearchCache` table from PostgreSQL

## Outcome

`LodSearchCache` is removed from PostgreSQL. Search cache now lives in Upstash Redis with automatic TTL expiry. This eliminates pgvector connection lock contention on cache reads and writes. TypeScript compiled cleanly when the phase was completed.

## Environment note

Add the following environment variables to your local `.env` file and to Railway if you want Redis-backed search history enabled:

```
UPSTASH_REDIS_REST_URL=<your-upstash-redis-url>
UPSTASH_REDIS_REST_TOKEN=<your-upstash-redis-token>
```

Current runtime behavior after the later resilience patch is graceful degradation: if these vars are missing, `getRedis()` returns `null` and the app continues without Redis-backed cache reads or writes instead of crashing during startup.
