## 1. THE DATA PROBLEM: 831 MB JSON File

This is the **#1 performance bottleneck** in the entire system.

### Current State

| File | Size | Load Into Memory | Parse Time (est.) |
| --- | --- | --- | --- |
| `master_registry.json` | **831 MB** | ~1.5 GB RAM (Python dict overhead) | **10-30 seconds** on startup |
| `graph_data.json` | 28 MB | ~60 MB RAM | ~2 seconds |
| `Categories.json` | 76 KB | Negligible | Instant |

### Why It's 831 MB

Each record stores a **768-float embedding vector** as a JSON array. A single record:

```json
{
  "image_embedding": [0.0123, -0.0456, 0.0789, ...]  // 768 floats × ~8 bytes/JSON float = ~6 KB per record
}
```

With ~5,000-10,000 records: `10,000 × 6 KB = ~60 MB of embeddings alone`. The remaining ~770 MB is JSON overhead (quotes, commas, whitespace, extra metadata fields).

### Impact

- **Startup**: 10-30 second cold start loading JSON
- **Memory**: ~1.5 GB RSS for Python process
- **No indexing**: Full array scan for search (numpy dot product is fast, but data load is not)
- **No persistence**: If the process crashes, all in-memory state is lost
- **No concurrent access**: Single Flask process, no connection pooling
- **Fragile**: One corrupted byte in the 831 MB file = total failure

## 2. DATABASE MIGRATION STRATEGY

### What Needs Relational Storage (PostgreSQL)

| Data | Current | Target Table | Fields |
| --- | --- | --- | --- |
| BIM Family Records | `master_registry.json` | `LodFamily` | id, name, category, lodLabel, provider, description, fileSizeKb, confidenceLevel |
| Image Embeddings | Inside `master_registry.json` | `LodEmbedding` | familyId, vector (pgvector `vector(768)`) |
| Graph Layout | `graph_data.json` | `LodGraphNode` | familyId, x, y, neighbors (int[]) |
| Categories | `Categories.json` | `LodCategory` | name, group, description, subcategories (json) |
| Search Cache | In-memory dict | `LodSearchCache` | queryHash, expandedQuery, ttl |
| Pipeline Runs | `pipeline_status.json` | `LodPipelineRun` | id, status, total, done, message, timestamp |

### pgvector for Embedding Search

Instead of loading all embeddings into numpy, use **pgvector** for native cosine similarity:

```sql
-- Install extension
CREATE EXTENSION vector;

-- Table
CREATE TABLE "LodEmbedding" (
  "id" TEXT PRIMARY KEY,
  "familyId" TEXT REFERENCES "LodFamily"("id"),
  "embedding" vector(768) NOT NULL
);

-- Index for fast ANN search
CREATE INDEX ON "LodEmbedding" USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

-- Search query (replaces numpy dot product)
SELECT f.*, e.embedding <=> $1::vector AS distance
FROM "LodEmbedding" e
JOIN "LodFamily" f ON f.id = e."familyId"
ORDER BY e.embedding <=> $1::vector
LIMIT 200;
```

**Benefit**: Eliminates the 831 MB JSON load entirely. Search queries go from "load all, compute, sort" to a single indexed SQL query.

## 3. SEARCH PERFORMANCE ISSUES

### Current: O(N) Full Scan

```python
scores = np.dot(self.embeddings, query_emb)  # N × 768 matrix-vector product
for i, rec in enumerate(self.registry):       # N iteration for keyword boost
    text_field = f"{rec.get('name_of_file',...}"
    matches = sum(1 for term in search_terms if ...)
    scores[i] += matches * 0.15
top_indices = np.argsort(scores)[-200:][::-1]  # Full sort of N scores
```

### Problems

| Issue | Impact |
| --- | --- |
| Full matrix dot product every query | CPU-bound, scales linearly with records |
| Keyword boost iterates all records | O(N) string matching |
| `np.argsort` sorts entire array | O(N log N) when only top-200 needed |
| OpenAI query expansion every uncached query | 500ms-2s latency |
| No result caching | Same query recomputed every time |

### Fix with pgvector

- **IVFFlat index**: Approximate nearest neighbor — sub-linear search
- **GIN index on tsvector**: PostgreSQL full-text search for keyword boost
- **Materialized view**: Pre-computed popular queries
- **Result cache**: `LodSearchCache` table with TTL

## 4. API DESIGN ISSUES

### Duplicate APS Integration

The LOD Checker implements its **own APS OAuth** (`aps_auth.py`, 230 lines) and **its own APS Data Management** (`aps_data.py`, 439 lines). The Dashboard already has:

- `server/auth.ts` — Autodesk OAuth provider
- `lib/aps.ts` — APS token + model derivative
- `components/families/BimViewer.tsx` — APS Viewer

**669 lines of Python will be replaced by existing Dashboard tRPC procedures.**

### No Authentication Integration

LOD Checker uses **Flask sessions** for auth. The Dashboard uses **NextAuth JWT**. Currently:

- LOD Checker doesn't know who the Dashboard user is
- Dashboard doesn't have access to the LOD Checker's Autodesk session
- Two separate OAuth flows for the same user

### No Error Handling Framework

All Flask routes use bare `try/except Exception` with:

```python
except Exception as e:
    return jsonify({"error": str(e)}), 500
```

No structured errors, no classification, no retry hints.

## 6. PIPELINE ARCHITECTURE ISSUES

### Not Deployable to Railway

The ML pipeline requires:

- **CUDA GPU** (SigLIP, BLIP2, SAM, GroundingDINO)
- **Python 3.12** with heavy ML packages (~5 GB venv)
- **Local file system** for image processing

This **cannot run on Railway**. The pipeline must remain a **local development tool** that:

1. Runs locally on a CUDA machine
2. Outputs processed data (embeddings, metadata, categories)
3. Uploads results to the Dashboard database via API

### Pipeline Status: File-Based Polling

```python
# Current: write to file, poll from API
status_path = ROOT_DIR / "00_data" / "pipeline_status.json"
```

Should be replaced with database-backed status + SSE push.
